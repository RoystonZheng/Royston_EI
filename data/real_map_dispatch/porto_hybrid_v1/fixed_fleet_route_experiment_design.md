## 1. 实验问题与边界

本实验比较三种路线决策方式，在同一真实地理路网、同一固定车辆订单序列和同一动态交通机制下完成任务后，实际经历的总时间与车辆资源成本有何差异。研究重点是：路线方法能否读懂单行、转向、信号和拥堵等地图特征，并把路线计算结果转化为合法且实际代价较低的道路 Link 序列。

这是**固定车队路线执行实验**，不包含订单派给车辆的调度层：车辆数预先固定，每辆车的订单和顺序在运行前冻结；车辆完成一单后，只能接自己序列中的下一单；不允许跨车转单、抢单、重排订单或加入中心派单器。

地图交通环境与车辆执行采用分离模块。交通环境持续推进信号相位、背景流量和道路状态；路线方法只能读取同一只读状态/预测接口，不能切换信号、改写背景车流或直接改交通参数。车辆在道路上行驶时仍会作为 SUMO 中的实体占用车道并产生进入/离开事件，从而影响共享队列；如果完全不把实验车的路段占用加入交通环境，实验车队造成拥堵在逻辑上无法实现。车辆模块因此仅通过行驶事件反馈占用，环境不接收车辆的路线偏好或控制命令。

保留 30 个热度候选点。候选点来自热度格中心，称为虚拟候选站点，不等同于现实运营站点。后续订单运行模块按固定随机种子生成端点：每 100 单中 70 单的上车、下车端点都来自候选池；其余 30 单可以有一个端点来自候选池、另一个是道路特征附近的模糊点，也可以两个端点都是模糊道路点。剩余 30 单内两种构成的具体比例尚未确定，须在正式运行前冻结，不在当前底图中预生成或展示订单端点。模糊坐标每个种子都不同，但在该种子的三种方法之间固定一致。

模糊点输入包含坐标、35 米不确定半径和道路特征提示；OSM way/node 真值只给独立匹配器，不暴露给路线方法。候选点及模糊点都要在路网冻结后匹配到一个或多个有向 Link。匹配器输出、路线方法输出和最终真值分别保存，避免把点位解析准确度混进路线搜索结果。

### 原始道路展示与 Link 筛选的边界

地图底图直接绘制候选 OSM 快照中的全部 7,278 条 `highway=*` Way，不以机动车道路白名单删掉原始线形。浅灰底线表示 OSM 原始道路线；叠加标记按当前展示规则分组：218 条含 `access`、`vehicle`、`motor_vehicle` 或 `motorcar` 的 `no/private` 标记为受限，41 条含许可、目的地、客户、配送、未知或条件准入标签的道路标为待核实，4,869 条不在当前机动车候选类别表内的 Way 以点线显示；其余 2,150 条只是机动车道路候选。该分组来自 OSM 标签，不等于现场通行核验；缺少限制标签不能证明道路允许本实验车辆通行，`private` 也表示需按授权规则判定。旧结构预检中的 2,179 条是较宽松的简化筛选计数，不能作为最终可行驶 Link 数；正式组网前要冻结准入规则并重跑预检。

显示道路仍不是实验路由图。正式处理顺序是先确定热度筛出的候选站点和订单模糊端点，再把每个点投影/匹配到附近原始道路及可能的有向路段，生成“点到道路”的接入连接；随后依据道路方向、机动车准入、转向限制和路网连通性，筛出实际可用的 Link 图。不会用端点间的直线冒充道路，也不会把地图上所有可见 Way 自动当作可行驶 Link。点位匹配、连接生成与 Link 排除原因均需留档，正式路线只能使用最终 Link 图。

### 地图订单数据包与展示计算

底图默认不含任何上下车热度点或筛选候选点。地图按 `map_order_demand_package` v1 JSON 契约导入数据；`pickup_points`、`dropoff_points` 保存所有聚合点，`demand_nodes` 与 `demand_pairs`（或逐单 `orders`）保存 OD 需求。当前演示包将 Porto 已完成出租车轨迹聚合为 840 个上车网格、866 个下车网格、22,977 个 OD 对和加权 355,525 次行程；不含司机/订单标识或原始轨迹，也不是正式固定订单。包结构和样例见 `map_import/README.md`、`map_import/map_order_demand_package.schema.json` 与 `map_import/porto-map-order-package-v1.json`。

候选筛选取上车点热度 Top N，并与所有达到用户设定计数阈值的点取并集；当前界面默认 Top 30、阈值 0（关闭）。导入后可分别显示全部上车点、全部下车点和筛选候选点。Dijkstra Link 按道路长度计算候选点间的有向最短路，遵守 OSM 单行方向，将共同经过的底层道路片段按被多少个候选点路线复用合并显示；点位接入取 300 m 内最近的机动车可路由节点。OSM 明确禁行、准入待核实以及不在当前机动车候选类别中的 Way 统一归入“机动车禁行／未纳入路由”一层，并排除出 Dijkstra 图；该层表示本实验路由规则，不等于逐条现场通行核验。当前预览尚未解析转向限制，因此 Link 图仍不是正式路线图。

拥堵层只对承载需求的道路片段着色。原型先把每个 OD 需求对通过基于长度的 Dijkstra 分配到一条基准道路路径，再按 `order_count` 累加各路段负载；路段估算同时加入负载归一化、仿真背景流量变化和邻近 OSM 信号位置的仿真相位/等待。时间滑块只驱动演示相位与背景系数，不代表真实实时信号、实时交通或真实通行时间；正式实验需用统一的 SUMO 时钟、背景车流和逐路段预测器替换该演示计算，并单独记录车辆真实通过时间。地图图层开关只保留 Dijkstra Link、机动车禁行路段、单行线（含方向箭头）、全部上下车点、筛选候选点、信号灯和需求拥堵；道路样式与方向箭头共用一个单行线开关。

## 3. 固定车队与任务文件

- 固定 10 辆车，每车 10 个订单，总计 100 单；正式设计为 10 个配对种子（0–9）。每个种子均按 70/30 生成：每车 10 单中 7 单为候选点到候选点，3 单属于道路特征模糊端点订单；模糊订单中可以有一个或两个非候选端点，细分比例须在正式运行前冻结。订单端点只在对应运行视图展示。
- 车辆初始位置从同一 30 点候选池按历史上车热度代理抽样。每个订单指定唯一 `vehicle_id` 与 `sequence_index`，不会在运行时重新分配。
- 车辆完成当前订单的下车段后，立刻为该车序列中的下一单发起路线规划。下一单规划时间计入总时间；车辆在规划完成前不出发，交通环境和其余车辆继续运行。
- 每个订单在规划时同时给出“当前车辆位置→上车点”和“上车点→下车点”两段路线。执行前需校验 200 条路线腿：100 条当单车辆位置到上车点，以及 100 条上车点到下车点。车辆位置在下一单开始时等于上一单下车点，所以不另加重新派单或空驶任务。
- 当前生成的订单文件只固定位置、归属和顺序；不含路线 Link、请求到达时刻、信号相位或实验结果。必须先通过最终有向路网的传统可达性门禁，才可冻结正式订单哈希。

如任一路线腿不可达，按预先登记的规则从同一候选池重新抽取对应端点，保持车辆归属、订单总数及按最新定义冻结的 70/30 类型分层不变；保留替换前后点位与原因，生成新的版本和哈希。所有方法收到同一份最终订单文件。传统路由器的预检路径只用于验证可达和约束，不得把该最优路径或其成本作为 LLM 输入答案。

## 4. 技术栈与模块接口

| 模块 | 实现建议 | 主要数据/职责 |
|---|---|---|
| 场景生成 | Python 标准库/Pandas、固定 seed | 30 个候选点、固定车辆初态、订单序列、模糊端点和源文件 SHA-256 |
| OSM/空间处理 | `netconvert` 导入 OSM；必要时用 pyproj/GeoPandas 核对几何 | 机动车 Link、单行方向、车道/限速/准入、转向限制、信号控制 connection |
| 交通仿真 | Eclipse SUMO、TraCI；SUMO 版本和配置冻结 | 连续推进信号计划、背景车流、车辆跟驰、排队、真实穿越时间和电耗 |
| 动态交通预测 | Python 只读 `TrafficForecast` 接口 | 根据计划出发时刻、相位进度、当前队列和冻结的背景需求预测逐 Link 时间/能耗；不读取未来真实仿真结果 |
| 传统路线方法 | 时变 Dijkstra（必要时 A*） | 在同一有向图和预测边权上按时间优先或能耗优先搜索 |
| 纯 LLM 方法 | 固定模型版本、结构化 Link/状态输入、JSON 输出 | 直接从已存在的 Link/连接关系提出合法有向路线；不允许虚构 Link，不以传统算法回退修复 |
| 本文方法 | Agent-readable 类型化地图接口 + LLM 路线候选 + 数学路线成本优化器 | LLM 读显式拓扑/转向/信号/状态关系并提出候选；优化器依预测目标选路；候选与最终路径均过独立验证器 |
| 记录与复核 | JSONL/Parquet、JSON Schema、SHA-256 | 输入快照、计算时间、仿真事件、逐路段预测/实际时间、路线合法性及最终成本 |

**共同交通状态接口**只读字段至少包括 `sim_time_s`、`link_id`、`movement_id`、`current_signal_phase`、`seconds_to_phase_change`、`queue_length_veh`、`observed_speed_mps`、`predicted_entry_time_s`、`predicted_travel_time_s`、`predicted_energy_wh`、`source_type`、`traffic_seed`。同一预测器对三组输出相同内容。三组可采用不同地图表示，但不得得到不同的道路事实或交通预测；记录每个规划请求的输入哈希。

本文方法的数学优化器只在 LLM 产生的合法候选路线中按被冻结的目标选择，不把不存在的 Link 补入图，也不改变信号或队列。纯 LLM 不调用全局派单器；传统方法不调用 LLM。三组路线生成失败、非法边或超时都记录为失败，正式比较中不使用另一组方法代跑。

### 动态环境与车辆事件接口

SUMO 仿真时钟按 1 秒步长推进，背景车流在整轮持续存在。OSM 的 `traffic_signals` 仅说明地图标记了信号位置，不含相位方案；由 SUMO 生成/配置的固定时制信号程序和偏移全部标为 `simulated` 并冻结。信号按时间持续变化，放行能力改变后，背景车和实验车排队随之形成/消散，进而改变实际路段通行时间。为保持模块边界，实验车辆不调整信号控制器；其实际车辆流量会自然进入同一路段的容量、跟驰和队列计算。

路线请求发生时读取当前状态并预测计划出发时刻的路段成本。记录规划开始 `t_plan_start`、规划完成 `t_plan_end`、路线计算耗时 `t_plan_end-t_plan_start`。车辆最早只能在 `t_plan_end` 出发；规划期间信号、背景流量和其他正在行驶的车辆继续推进。每次道路穿越记录车辆实际进入和离开时间，以进入至离开间隔为该车该 Link 的实际旅行时间。主实验不在订单中途重规划；每辆车到达下车点后才规划自己的下一单。

时变路径代价按预计进入每条 Link 的时刻查询预测器，因此路径前段的信号等待/排队预测会改变后续边的预计进入时间和成本。每单规划耗时包含路线搜索或 LLM 推理、地图查询、本文方法的优化器以及输出校验；实验前的一次性点位绑定和可达性预检另记为场景准备成本，不算进车辆行程时间。

实现时，交通环境运行在独立的仿真进程/事件调度器中，路线方法只订阅状态并提交路线结果。若为加速离线运行而用离散事件方式回放，必须把测得的规划延迟作为该车辆的模拟等待时间，并让其余信号、背景车流和车辆事件在这一模拟时间段继续推进；不能暂停全图时钟来等待 LLM。

## 5. 三种路线方法与目标

| 组别 | 路线选择方式 | 公平性控制 |
|---|---|---|
| R1 传统算法 | 时变 Dijkstra；按当前实验目标，在每单开始时用共同预测器的 Link 时间或能耗搜索两段路线 | 使用完整有向 Link、信号与拥堵预测；不允许用静态距离当作唯一成本 |
| R2 纯 LLM | LLM 根据已有有向连接和相同预测状态直接规划两段路线 | 固定同一模型、上下文预算、输出 schema；本地只校验，不替模型重规划 |
| R3 本文方法 | LLM 通过类型化 Agent-readable map 查询道路/状态并给出候选路线，再由数学优化器按当前目标选取 | 模型与 R2 固定相同；同一预测数据与硬约束；优化器耗时计入规划耗时 |

如需将性能差异归因于“地图可读性”，R3 还需配对一个仅把地图查询输出改为扁平 Link 表、其余 Agent/优化器/提示/model/schema 完全相同的表示消融。只有这个配对差异能较干净地检验地图表示本身；R1/R2/R3 的总系统比较还同时包含算法角色差异。

每次规划都生成时间优先与成本优先两种候选选择结果，避免把秒、Wh、token 和 CPU 时间用未经依据的权重混成一个分数：

1. **时间优先：**最小化包含信号等待和队列预测的总预计行程时间。
2. **成本优先：**最小化统一电动车能耗模型的预计 `kWh`；成本模型使用预测速度/停车与加速状态，红灯和拥堵可改变能耗估值。SUMO 的电动车模型和其参数须在正式试验前固定，所有方法同车同参数。

两种目标分别运行在同一订单和交通种子副本上。最后分别报告实际模拟时间、实际模拟能耗、行驶距离，以及规划耗时和模型 token/API 资源。未冻结电价时不把 kWh 换成货币，也不跨单位加权。若 SUMO 电耗模型尚未通过参数校准，成本结论暂以实际距离与延误分项呈现，不能写成实际运营费用。

正式主矩阵为 3 种方法 × 2 个目标 × 10 个 seed。若 R2、R3 各对每个订单/目标只发一次模型请求，预计上限为 4,000 次规划请求（不含预检，默认不重试）；正式 LLM 批次前须另行冻结模型版本、单次输入/输出预算、总请求上限和费用熔断。当前没有发起任何模型请求。

## 6. 时间、拥堵与运行机制

地图状态从仿真 `t=0` 起连续运行，和车辆当前有没有路线无关。路线计算延迟进入车辆时钟：车辆在规划完成前不走；仿真环境不等待该车，而继续运行其他事件。因此最终完成时间包含该车各次路线计算等待和实际路段通过时间。车队数量、初始位置、背景车流、信号程序和随机种子在每种方法间相同。

每个方法、种子和目标都使用独立的 SUMO 副本；信号程序、背景流 OD/出发时序和随机种子成对一致。由于各方法选的路线不同，实验车队本身造成的排队会不同，这是闭环总系统效果的一部分。解释路线方法时必须分开报告“共同外生背景交通”与“实验车队引起的额外队列”。同一方法内回放时，所有信号、背景车和车辆路径由相同种子重复，保证可重现。

主情景采用中等背景需求；低/高需求作为敏感性分析。具体车流规模不凭空设成 Porto 实测值：先用现有历史热度/OD/时间段作需求形状代理，在 SUMO 网络规模和路口饱和状态检查后冻结流量级别。正式报告标注为历史代理校准的仿真需求。SUMO 自动生成的信号程序不声称等同真实 Porto 配时；信号周期、相位和偏移配置都保存并标 `source_type=simulated`。

## 7. 评价指标

**主要结果：**

- 车队完成时间 `fleet_makespan_s`：仿真开始到最后一辆车完成其固定序列的时间。
- 车辆总经历时间 `sum_vehicle_elapsed_s`：各车从第一次规划开始到完成第十单的时间之和。
- 逐订单端到端时间：路线计算延迟 + 车辆从当时位置到上车点的实际行驶 + 上车点到下车点的实际行驶；不包含不同方法不一致的乘客服务时间。
- 车辆运行资源：总 `energy_kwh`、总 `distance_km`；规划资源单列为 CPU/LLM 墙钟时延、token、调用次数和配置费估算。

**诊断指标：**路线预测时间/能耗与 SUMO 实际值误差、信号等待秒数、队列延误、每条 Link 的进入/离开时刻、路线连续性、单行/转向违规率、未完成订单数、格式失败/超时/非法候选数、规划延迟分布。预测成本和实际成本分开保存。

主结论按“方法 × 目标 × 背景需求档”列出每个种子的原始结果、配对差、均值/中位数、离散程度和配对置信区间。时间和成本分别报告，不把统计上不显著的差异说成性能提升。非法路线不进入仿真，仍计为该方法的失败并保留在成功率分母中。

## 9. 实验前门禁和当前状态

1. 校对 UCI/Figshare 计数差异，冻结候选围栏与 30 点池。

## 10. 主要技术来源

- SUMO 的 `netconvert` 支持将 OSM XML 转换为 SUMO 路网：[官方文档](https://sumo.dlr.de/docs/netconvert.html)；OSM 导入后的自动信号方案可能不同于现实，正式相位需单独保存并注明模拟性质：[Traffic Lights](https://sumo.dlr.de/docs/Simulation/Traffic_Lights.html)。
- SUMO 的队列输出可以记录排队时间和长度：[Queue Output](https://sumo.dlr.de/docs/Simulation/Output/QueueOutput.html)；路由权重支持随时间变化的 travel time：[Routing](https://sumo.dlr.de/docs/Simulation/Routing.html)。
- SUMO 电动车电量设备需要结合能耗模型与车辆参数设置，并可读取电力消耗：[Electric Vehicles](https://sumo.dlr.de/docs/Models/Electric.html)。参数需本实验预先冻结，不能拿默认值冒充 Porto 实车标定。
- Porto 热度和 OSM 许可说明沿用旧版方案的 UCI、Figshare、OSM 来源记录；详见 [旧版真实路网派单综合实验设计](真实路网派单综合实验设计_20261022.md)。
