# 后续论文思路与系统结构

作者：郑睿涛  
日期：2026-10-02  
状态：课程作业研究草案。以下内容是推荐方案，不是已经实现的系统或已经证实的创新。

## 一、选题落在哪里

**暂定题目：面向动态服务目标的可验证多智能体无人网约车调度研究。**

系统基础沿用此前讨论的“路线感知、服务承诺约束下的多智能体滚动调度”。在此基础上，把论文重点放在一个问题上：

> 当运营方改变服务要求时，怎样把要求对应到地图、订单和车辆状态，检查其含义与可行性，再让多辆车协调执行，同时避免新目标破坏已有乘客的服务承诺？

例如，运营方提出：“优先接送体育馆散场乘客，同时不要让其他区域的乘客等太久。”系统需要明确体育馆对应哪个区域、“优先”影响哪项指标、“等太久”有没有已批准的阈值。若信息不足，应询问或沿用明确获准的默认规则，不能让 LLM 随意填一个数。

即使要求已经明确，也可能没有足够空闲车辆满足它。此时应报告哪些条件无法同时满足，提出需要确认的调整建议，不能擅自放宽已有服务承诺。

### 研究范围

- 已知路网，动态订单和车辆状态；路线时间随新交通信息更新。
- 每辆车是一个维护自身状态、生成可行接单候选的智能体，由协调器统一解决订单冲突。
- 暂不默认采用拼车。拼车论文可提供方法参考；采用多人共享行程前，需另行定义容量、绕行和上下车顺序。
- 不研究车辆感知、转向控制、行人轨迹跟踪，也不要求先训练 CNN、GNN 或强化学习模型。
- 历史热点预测、空车调位可作为后续扩展，不抢占当前核心问题。

## 二、创新点怎么表述

**候选创新点：结合路网与车辆状态的调度目标检查及反馈修正机制，使目标调整在已有服务承诺的约束下进入多车调度。**

这里的“机制”需要有明确方法，至少回答三件事：

1. **要求怎样表达。** 将服务对象、区域、有效时间、评价指标、优先级和参数来源记录为结构化目标；区分硬约束与软偏好。
2. **错误怎样定位。** 分清地点无法对应、含义不清、参数缺失、规则冲突和当前运力不足，不能只检查输出是不是合法 JSON。
3. **反馈怎样修正。** 将检查得到的具体原因交给目标解析模块；不能自动决定的内容交给人确认；保留修改记录，失败时使用已批准的规则重新调度。

目前只能称为候选贡献。要成为论文创新，还需证明相较已有方法，它处理了哪些此前未充分解决的情况，或者取得了可复现的质量、成本或可靠性改善。把模块连接起来、增加提示词、使用某个新模型，都不足以单独证明创新。

特别需要避开已有工作：自然语言转目标函数已有 [RideAgent](https://arxiv.org/abs/2505.06608)，形式化任务再调用规划器已有 [LLM+P](https://arxiv.org/abs/2304.11477)，离线生成可复用调度策略已有 [RideSkill](https://arxiv.org/abs/2609.02250)。乘客公平性也已有研究，例如 [HCRide](https://www.ijcai.org/proceedings/2025/1143)。本文需要围绕明确的新问题和方法建立区别，不能把这些能力分别列为原创。

“可验证”在本草案中仅指预先定义的检查和优化模型中的约束满足。自然语言解释仍可能错误，真实路况也可能超出预测；没有形式化证明时，不能宣称完整正确性或实际服务绝对保证。

## 三、系统整体结构

系统分成两条流程。运营目标改变时才需要解析目标；普通订单到来时，直接使用已批准的目标调度。

```text
较低频率：运营目标更新
运营方要求 + 相关地图/业务事实 + 已批准规则
    -> 上下文与提示词组织
    -> LLM 输出结构化服务目标
    -> 地点、含义、权限、规则与可行性检查
    -> 通过：保存有版本和有效范围的目标
    -> 不通过：返回具体原因，修正或请人确认

较高频率：车辆与订单调度
最新订单、车辆状态、路网与交通信息
    -> 路线模块计算候选路线和预计成本
    -> 各车辆智能体生成可行接单候选
    -> 按已批准目标与评分规则评价候选
    -> 数学优化器协调多车分配
    -> 执行安排并记录结果
    -> 更新状态，进入下一轮

执行反馈 -> 更新状态和可行性判断
目标本身需要调整时 -> 回到目标更新流程
```

LLM 不在每次调度的必经路径上。移除 LLM 后，可由人填写同样的结构化目标，系统仍能运行。已批准的目标可以复用，但车辆候选、路线成本和可行性必须根据当前状态重新计算。

### 各模块负责什么

| 模块 | 输入 | 输出与责任 |
|---|---|---|
| 地图与状态服务 | 路网、区域、合法上车点、交通、车辆、订单 | 带时间戳的统一事实；将观测、预测和未知值分开 |
| 路线与时间估计 | 候选车辆、订单、现有行程、路况 | 可达性、候选路线、预计接送时间与新增成本 |
| 上下文与提示词 | 要求、相关事实、规则、输出格式 | 给 LLM 的有限上下文，不默认塞入整张城市地图 |
| 目标解析 | 自然语言与上述上下文 | 结构化目标、待确认项；不直接下发车辆分配 |
| 目标检查与修正 | 目标、状态快照、已有规则 | 通过、缺信息、冲突或不可行，以及对应原因 |
| 评分规则库 | 已批准目标、车辆候选及成本 | 候选分数；使用预设且含义明确的指标和参数范围 |
| 车辆智能体 | 自身位置、状态、承诺与候选订单 | 可执行的接单候选及成本，执行被选中的安排 |
| 数学优化器 | 各车候选、分数、约束 | 无冲突的联合分配，以及待服务订单和求解状态 |
| 执行与监测 | 计划、车辆行动、实际时间 | 更新状态，记录偏差、服务结果与计算开销 |

## 四、几个容易混淆的地方

### 地图能被 Agent 读取，具体指什么

当前建议使用可查询的道路图和结构化事实，例如“体育馆东门对应上车点 P17；道路 E8 当前封闭；车 2 正在送客”。LLM 读取完成当前目标解析所需的信息；路线模块读取路网计算路径。

可以借鉴 LM-Nav 的语言与地标对应、VLMaps 的语言可查询空间表示，但不需要照搬视觉建图系统。已知地图也不代表知道未来订单；预测必须标注为预测。

### LLM 输出评分规则，还是目标函数

首版建议更受控：**LLM 输出结构化目标和获准的偏好参数，程序据此组装评分规则及优化目标。** 不让 LLM 在线任意生成并执行 Python 函数。

例如，它可以表达“本时段优先降低指定区域乘客的等待时间”，并选取允许使用的指标。指标单位、归一化方式、可选优先级和参数范围由程序预先定义。没有依据的等待上限不能直接生成。硬约束由规则系统维护，不能通过修改权重把它变成可忽略的偏好。

这使 LLM 成为一个可替换的目标解析模块。其是否优于表单或规则解析，仍要单独验证；它不一定值得保留。

### 路线是否可以在分配前算完整

可以。候选数量允许时，路线模块可提前计算每个候选安排的完整路线和预计成本，再交给优化器选择。限制在于候选组合可能很多，而且计算依据只是当前信息。新订单和路况到来后需要更新，不能把这次的完整计算当成对未来的确定预知。

### 多智能体怎样体现

各车辆智能体根据自身状态和承诺提出可行候选，协调器解决多车争抢同一订单等冲突。这是“车辆局部决策加集中协调”的设计，不是完全分布式系统，也不等于多智能体强化学习。

仅给车辆对象命名为 Agent 不构成贡献。后续应解释局部候选生成带来了什么作用，必要时与统一集中生成候选的版本对比。

### 承诺与异常怎样处理

已接到的乘客不能因新订单或新目标而被随意放弃。上车前是否允许换车，以及允许的额外等待，应由事先确定的服务规则规定。行驶中可以调整路线，但仍需检查相关限制。

目标无效、优化问题不可行和求解超时是不同情况，要分别记录。LLM 失败时，回退到已批准的目标，并按最新状态重新寻找可行安排，不能直接执行过时计划。真实拥堵导致承诺难以兑现时，要记录偏差并触发既定异常处置；不能通过修改阈值掩盖违约。

## 七、将来用什么证据支撑论文

这一节是后续验证方向，不是今天新增的执行作业。

比较时保持路网、订单、车辆、信息权限和基础优化器一致。可比较人工确认的结构化目标、LLM 解析后仅检查格式的目标，以及加入状态检查和反馈修正的目标。所有版本都保留最终调度的硬约束检查，不能靠取消对照组的基本保护制造优势。

重点观察三类结果：

1. **要求理解与错误处理：** 地点和参数是否正确、冲突能否发现、必要时能否提出澄清、修正后是否符合人工核定的要求。含糊目标可能有多个合理解释，应先制定判定依据。
2. **乘客与车队结果：** 等待时间及其分布、订单服务率、承诺违反情况、空驶成本。不能只统计已完成订单而忽略未服务订单；需要按区域检查时另行定义公平性指标。
3. **运行代价：** 从收到要求到可用目标的完整耗时、普通调度耗时、API 调用量与 token 成本；超时和失败也要纳入统计。

A*、Dijkstra 是路线计算方法，不能单独作为整个车队调度的对照。调度层可采用明确的就近可行分配、固定目标优化等方法；若对比学习方法，应匹配任务设定并披露训练成本。还需要检验 LLM 相较结构化表单或规则解析是否有实际价值。
