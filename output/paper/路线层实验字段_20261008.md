# 实验方案：Agent 候选、调度轮次与执行结果字段草案

日期：2026-10-08  
状态：实验设计草案，待逐项确认。  
适用范围：一对一动态无人网约车；允许车辆在当前订单执行期间预留一笔下一订单，但当前订单服务承诺保持硬约束。

## 0. 字段使用规则

- **必填**：每条记录都必须有值。
- **条件必填**：只有满足指定条件时必须有值；不满足时写 `null`。
- **可空**：该信息可能在某些方法或场景中不存在；字段仍保留，使用 `null`。
- 数组无内容时使用 `[]`，不要省略字段。
- 所有时间使用同一仿真时钟；距离使用米；时间使用秒；能耗使用 kWh。
- LLM 不能修改最大等待时间、已有服务承诺等硬约束。硬约束结果由程序和优化器复核。

## 6. 当前字段设计中的关键规则

1. `current_order` 和 `candidate_order` 必须分开，不能共用一组时间字段。
2. `vehicle_available_time` 是时间点；`idle_duration_before_next_pickup_sec` 是时长，不能混用。
3. `next_wait_slack_sec` 是硬约束余量，不能被 LLM 通过调整权重抵消。
4. 候选成本优先保留向量，不直接压成一个无法解释的总分。
5. 路线、时间、距离、能耗和硬约束结果由程序计算或校验；LLM 可负责语义转换、候选建议和解释。
6. 预测值和实际值分别记录，不能用预测值替代执行结果。
7. 未服务订单、超时订单和优化器超时必须保留记录，不能过滤掉。

## 2.8 情境自适应候选筛选函数（新增设计）

候选筛选不固定为单一距离半径或固定 Top-K。LLM 可以根据结构化场景特征生成函数表达式、函数参数或函数选择结果；运行时由程序计算函数，数学优化器负责范围限定、分类和硬约束检查。

### 2.8.3 函数执行原则

1. LLM 输出公式、受限表达式树或已注册函数参数，不直接执行任意代码。
2. 数学优化器限定阈值、候选数量、服务承诺和最大等待时间。
3. 函数运行时只读取当前状态快照，不读取未来订单信息。
4. 函数生成失败、超时或越界时，使用已批准的回退函数，并记录原因。
5. 与固定半径、固定 Top-K、人工设计的自适应函数使用同一地图、订单、车辆和优化器进行比较。

## 2.9 路线候选数量的首版规则

首版不强制每个方法输出 Top-K 路线。每个车辆—订单组合至少需要输出一条经过验证的路线；`alternative_route_refs` 可以为空数组。A*、Dijkstra 等传统算法通常直接输出一条最短路线，后续如需比较多路线候选，再单独引入 Yen/Eppstein 等 K 短路方法，并保持所有方法相同的 K 和验证规则。

## 2.11 路线层比较口径

每轮实验的地图、道路、信号灯、边界和拥堵状态只作为场景图标注与输入元数据，不作为方法优劣的直接比较项。同一轮内所有方法读取同一场景。

路线层主要比较：

- 路线有效性、可达性和指定上车点抵达率；
- 预计接驾时间、送达时间及其误差；
- 路线距离、信号灯/拥堵影响和预计电耗；
- 路线搜索、Agent 判断、LLM 调用、路线验证和总决策时间；
- API/模型调用成本、算力成本和车辆运行资源成本；
- 输出解析失败、无可行路线、超时和重规划次数。
- 语义任务的候选节点/边偏差、道路侧匹配、绕行距离和掉头次数或其可复现代理指标；语义解析失败与路线不可达分开统计。

地图与道路字段仍保留在每轮场景记录和图示中，但不直接汇总为“地图表示得分”。不同成本量默认分开报告；只有在明确电价、算力价格和 API 计费口径后，才可以额外计算货币金额。

## 2.14 统一路线输入与可变路线输出

精确节点任务中，所有路线方法必须读取完全相同的 `RouteInputPackage`，该输入包由地图查询模块在方法运行前生成，不由任一待比较方法临时决定。语义地点任务中，所有方法读取相同的原始语义输入、道路图和任务元数据；解析器分别生成候选节点后，再为该候选构造路线搜索包并交给相同的验证器。评估器真值保存在独立记录中，不能作为任一方法的输入。

输入包至少包含：

- 起点、指定上车点和指定下车点；
- 同一批道路节点和道路边；
- 节点坐标、地标、合法上车/下车标记；
- 道路长度、基础速度、单向、拥堵等级和信号灯延迟；
- 地图版本、道路状态版本和随机种子。

Dijkstra、A*、纯 LLM 和 Agent 工作流可以输出不同数量的路线，不强制 Top-K。实验应记录：

- `route_output_count`：输出路线数量；
- `valid_route_count`：通过验证的路线数量；
- `invalid_route_count`：非法路线数量；
- `route_generation_timeout`：是否超时；
- 所有有效路线的距离、时间、电耗和计算成本；
- 最佳有效路线、平均有效路线和首条路线的结果。

为避免输出更多路线带来不透明优势，所有方法使用相同的最大运行时间和验证规则；使用 LLM 的两组再使用相同的输出 token 上限。输出数量作为结果字段单独报告。

### 局部输入包生成规则（已确认）

全局仿真地图为 100×100。每个路线任务以起点、上车点、下车点的最小包围区域为基础，四周先扩展 10 个网格单元。如果提取的局部图不连通，每次再扩展 5 个单元，最多扩大 3 次。精确任务的扩展在路线方法运行前完成，所有方法读取同一份最终局部输入包；语义任务先固定原始文本和图范围，再由各方法的候选端点触发同一扩展规则。每个输入包记录最终扩展次数、节点数、边数和序列化后的 token 数；全图 Dijkstra/A* 结果可另作参考，不混入局部输入方法的主比较。

语义地点任务的地点文本直接呈现给所有方法，不呈现正确节点 ID。传统基线固定使用 `graph_only` 解析器，只读地标名称/别名、坐标、方向/邻近和合法上下车点，不读路牌/电线杆语义；Agent-readable 组可读取 `RoadFeatureInputProtocol v1`。解析候选与评估器真值分开记录，候选与真值不一致不自动判定路线无效；`pickup_exact_match`/`dropoff_exact_match` 仅是评分字段。
