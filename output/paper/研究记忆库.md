## 1. 研究对象与问题边界

### 已确认

- 研究对象是一对一无人网约车（autonomous ride-hailing）动态派单，不是拼车或多人共乘。
- 每辆车同一时刻服务一名乘客；完成当前订单后，可以再接受后续订单。
- 研究关注多个无人车如何协同分配动态到达的订单，并规划车辆驶向乘客指定上车点的接驾路线。
- 需要区分：
  - 订单分配/派单：决定哪辆车服务哪个订单。
  - 路线规划：规划车辆如何抵达指定上车点及后续目的地。
  - 车辆再平衡：将空闲车辆主动移动到潜在需求区域。再平衡不是当前研究的中心问题。
- “接驾准确度”指车辆能否按路网规则到达乘客指定的上车点，不表示可以擅自更改乘客上车点，也不等同于推荐替代上车点。
- A*、Dijkstra 等是路线搜索算法，不能单独代表完整的车队派单系统。

## 2. 研究主线与架构

### 用户已确认的三条研究主线

1. 设计用于无人网约车调度的多 Agent 策略工作流。
2. 设计多 Agent 与不同技术模块、数学优化器结合的协同派单框架及程序实现。
3. 设计 Agent 友好的地图表示和道路特征，让车辆 Agent 能读取、查询并利用路线决策所需的信息。

这些是论文要论证和验证的研究主线，不等于已经证明的创新或效果。引言、摘要和结论中不得在文献比较或实验完成前宣称“首次提出”“优于所有方法”或“解决了某问题”。

### 当前架构约束

- 每辆无人车对应一个 Agent 是硬性要求。
- 每车 Agent 的工作流中包含 LLM 环节；LLM 不直接作出全局最终派单决策。
- 全局车辆—订单分配由数学优化器参与并负责求解。
- Agent 的路线评估与全局派单优化器应通过明确接口交互，例如把可达性、候选路线预计时间、距离或资源代价传给全局优化器。
- 尚未确定 LLM 在 Agent 内的具体职责、调用频率及运行模型。不能假设每辆车在每轮派单都调用 LLM，也不能把 LLM 固定为“生成路线评分函数”或其他未经确认的角色。
- 路线生成/评估可能由训练模型或传统算法完成，需通过后续对照或消融研究选择；引言当前只写成待比较的实现选项。

### 用户确认的分层对照（2026-10-07）

- 路线层：比较 A*、Dijkstra 等基础算法、单 LLM，以及 Agent + Agent-readable map + 道路特征组合；同一实验组固定模型类型，后续再改变模型或 Agent 配置。
- 车队派单层：比较直接由 LLM/API 决策、多 Agent 工作流，以及多 Agent 加数据驱动全局优化器。
- 课程讨论对应时间：路线对比 14:59–17:17、01:06:08–01:08:34；派单对比 01:04:12–01:04:57；先固定模型、再改变模型或 Agent 01:05:15–01:05:57。指标讨论 57:35–01:02:05，涉及匹配成功率、调度耗时、积压、车辆负载和利用率。证据类型：用户提供的课程逐字稿时间戳及链接，尚未独立复核逐字稿原文。
- 在固定地图、订单、车辆和求解器的条件下比较普通地图表示与 Agent-readable map，是本项目的实验设计建议，不是教师指定的基线；需通过实现确认控制变量。

## 3. Agent 友好地图的定位

### 已确认的方向

地图层不能只写成“给优化器提供结构化约束输入”。研究重点可以是地图面向车辆 Agent 的表示、查询方式及其与路线评估/派单优化器的接口。

当前可采用的研究表述：

- 输入是预先给定的道路网络及场景条件。
- 地图表示可组织道路节点与连接关系、道路通行属性、预设障碍及可配置约束。
- 车辆 Agent 可以读取或查询完成接驾所需的局部地图状态。
- 路线模块据此评估指定上车点是否可达，并形成候选路线的预计时间、距离或资源代价。
- 将可行性和成本指标以统一结构传递给全局数学优化器，供多车派单比较。

这使地图成为连接“单车接驾路线评估”和“全局订单分配”的中间表示。其具体表示形式、查询接口及实际优势尚待实现和实验验证。

### 场景复杂度限制

- 教师建议：目前没有一套开源数据集同时完整覆盖路网、网约车订单、信号灯、动态拥堵、封路和路边地标；建议使用确定好的障碍和自设约束，把重点放在多 Agent，避免场景与代码复杂度过大。这是用户提供的教师建议，尚未独立验证“没有任何此类数据集”的绝对命题。
- 当前模拟范围优先采用已知路网、预设/静态障碍和可配置场景约束。
- 暂不承诺实时摄像头感知、行人/车辆检测、街景地标识别、交通灯视觉理解或动态封路感知。
- Agent 友好地图的贡献在于“怎样组织并提供这些已知路网信息”，不在于堆叠更多种类的真实世界数据。
- 不得声称地图表示“保证完美到达”。应通过模拟指标检验路线可行率、指定上车点抵达率等。

## 4. 优化目标与评价口径

### 当前用户决定

- 时间优先，成本随后优化；时间优先级是严格的。
- 当前按以下操作性定义撰写：乘客等待时间 = 调度计算/决策时间 + 车辆从当前位置驶到指定上车点的运行时间。
- 最大等待时间是硬约束，不应当作为可被低成本抵消的普通加权指标。
- 成本不是乘客支付的票价，指系统资源成本，按时间目标之后的资源目标处理：
  - 用户确认计算开销以模型消耗额度计量，并采用预训练模型与 DeepSeek V4 Flash 配置；具体模型标识、版本、服务端额度接口或本地 tokenizer 统计口径仍待固定。跨平台额度若单位不同，应分别列报，不直接相加。出版方文档事实（核对日期 2026-10-07）：DeepSeek API 当前模型名 `deepseek-flash` 对应 V4.1-Flash，旧名 `deepseek-v4-flash` 仅作为兼容名并被路由到 V4.1-Flash；API 价格按 token 计费且可能随峰谷时段变化，需记录请求时的模型名、实际版本、token 用量和计费时段。[官方更新记录](https://api-docs.deepseek.com/updates/)；[模型与价格](https://api-docs.deepseek.com/quick_start/pricing/)。若用户要求测试历史 V4 Flash 本体，应另行确认可复现的模型来源。
  - 用户同意车辆按电动车模拟，并授权采用通用能耗计量口径。方案建议采用 kWh/100 km 电能消耗率，固定参考车型能耗率 e，以 E=d·e/100 估算路线耗电；参考车型和 e 值尚待确定。GB/T 18386.1—2021 可作为试验方法依据：[国家标准信息页面](https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=018D351EFF1AACD87C5919D0F21BEEBE)。这是简化模拟指标，不是实时车辆能耗模型。
  - 由于模型额度与电耗不适合直接跨量纲加总，方案建议在平均等待时间最优的解集中分别报告调用额度与 kWh，并比较 Pareto 非支配解；若实验要求单一方案，还需在方法部分明确选解规则。
- 用户确认的优先级为：最大等待时间硬约束下先最小化平均等待时间，再处理资源消耗。以上向量/Pareto 口径是方案建议，需在方法设计中确认实现方式。

### 成本定义确认（2026-10-08）

- 用户确认项目中讨论的成本定义均保留，后续方法和实验需要分层报告：
  1. **时间指标**：调度/决策响应时间，以及车辆驶向指定上车点的运行时间；乘客等待时间按两者之和统计。
  2. **系统计算成本**：优化器求解时间、重复求解与超时、LLM/API 调用次数、token 或模型额度消耗。
  3. **车辆运行成本**：空驶距离、空驶时间、车辆负载相关资源，以及按电动车能耗率估算的电能消耗。
  4. **候选路线成本**：预计接驾时间、空驶距离、预计送达延误和区域服务偏差等候选项；现有加权公式仍需确认权重和归一化方式。
- 最大等待时间和已有服务承诺属于硬约束，不作为可被资源成本抵消的普通加权项。
- 模型额度、求解资源、距离、时间和 kWh 不在没有依据时直接跨量纲相加；默认分别报告，若需单一选解再明确层级/Pareto 规则。证据类型：用户确认；具体权重、参考车型、统计窗口和选解规则仍待方法设计固定。

### 实验报告约束

- 若某些模拟场景下供需不足、最大等待阈值不可行或订单无法服务，必须记录超时、未服务订单或积压；不可预设所有订单都能被服务或积压恒为零。
- 服务率、等待时间、积压、车辆负载、计算时延/资源消耗是已讨论的候选指标；最后采用哪些指标仍需实验方案确认。
- 平均等待之外是否报告最大值、分位数等统计量，待确认。

## 5. 模拟与证据边界

- 用户已说明实验采用模拟实验，不做真实道路实验。
- 用户会寻找可用数据；若找不到适合的数据，考虑自建/模拟数据。数据源与最终实验地图尚未确定。
- 教师建议将路网条件作为场景约束，优先固定障碍并配置约束；不得写成已拥有完整真实路况数据。
- “研究设计”“程序实现”“单路线 Demo”“模拟实验结果”“真实部署结果”是不同证据等级，必须分开描述。
- AIFP、GridRoute、DualAD 等材料偏向机器人导航或单车路径规划。它们可启发地图表示、候选路线检查和反馈修正，但不能替代多车网约车派单文献或派单实验。
- 本地路径规划 Demo 复现记录不能作为车队派单效果的证据：output/paper/两个Demo复现记录.md。

### 文献写作原则

- 先写研究脉络和任务差异，不逐篇摘要堆砌。
- 不声称传统优化或强化学习无法处理动态需求；已有工作覆盖在线匹配、长远价值、多车协同与动态运营。
- 不把路径规划方法等同于完整派单方法，也不把车辆再平衡与订单分配混为一谈。
- Agent 友好地图需通过比较现有地图表示/导航工作来确定真实差异，不能宣称“第一次让地图可被 Agent 读取”。
- LLM+优化器已有直接相关工作，需比较 LLM 职责、优化层级、Agent 粒度、地图/路线接口和目标函数，而非笼统宣称组合创新。
- 文章支持的结论应按论文实验场景描述，不把某论文报告的百分比迁移成本文预期效果。
