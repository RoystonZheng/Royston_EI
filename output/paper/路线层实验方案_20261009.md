## 0 . 一句话总结 
路线层先在 100×100 的离散道路图上生成多轮随机场景。每个车辆—订单任务先由中立地图查询模块生成相同的原始路线输入包，再由各方法完成地点解析和路线规划。Dijkstra、A*、Codex CLI 纯 LLM 和项目定义的车辆 Agent 工作流都经过同一套路线合法性、上下车点精准性、拥堵/信号灯、电耗和成本评估。首轮重点比较路线结果、计算时间、模型用量估值和车辆电耗，不在路线层做全局订单分配。30% 语义地点任务是难度控制项，不是传统算法的排除条件：传统基线使用固定的图规则语义解析器；R3 纯 LLM 使用普通拓扑与 graph-only 图结构输入，R4 Agent 工作流读取 `RoadFeatureInputProtocol v1` 的道路特征语义。所有后续模型组统一用 Codex CLI，历史 DeepSeek 结果保留并与新结果分开报告。各组都必须尝试生成路线。传统算法和纯 LLM 如果在某些环节表现更好，将作为 Agent 工作流的可替换路线工具，而不是被预先排除。

## 1. 实验目标

路线层只研究一个车辆面对一个候选订单时，能否根据统一的道路输入生成一条或多条合法路线，并准确抵达指定上车点和下车点。

主要验证：

1. 传统路线算法、纯 LLM 路线规划和车辆 Agent 工作流的路线结果差异；
2. Agent 工作流中的状态读取、地点映射、路线生成、检查和反馈重规划是否有实际作用；
3. 在所有方法都可运行的前提下，比较图规则基线和 Agent-readable 道路特征输入对上车点/下车点候选质量、绕行/掉头和路线可行性的影响；
4. 红绿灯、拥堵和电耗如何影响路线结果；
5. 不同方法的计算时间、API/算力成本和车辆运行成本。

本阶段不决定哪个车辆最终接哪个订单，不比较订单服务率、车队积压或全局车辆—订单分配。这些内容进入调度层实验。

## 2. 实验边界

- 每次路线任务对应一个车辆—订单组合。
- 订单已经分配给该 Agent 作为候选输入；路线层不作最终订单选择。
- 精确节点任务中每个方法接收完全相同的 `RouteInputPackage`；语义任务中每个方法接收完全相同的原始语义输入包、道路图和可见性规则，随后由各自的地点解析器生成候选端点，再交给同一套路线搜索和验证器。
- 方法可以输出不同数量的路线，不强制 Top-K。
- 每个方法至少要输出一条经过验证的路线，或明确输出不可行/失败。
- 同一轮使用同一张地图、同一组道路状态、同一辆车位置和同一订单起终点。
- 不在路线层改变订单流量、订单到达过程、局部订单密度和需求/供给比。
- 订单起点和终点可以在不同轮次随机生成，但同一轮内对所有方法完全一致。
- 路线任务中 70% 使用精确上车点/下车点节点 ID，30% 使用语义地点表达；语义任务固定包含“地标附近”“地标相对位置”“道路特征位置”三类简单句式，并由评估器保留对应合法节点真值。语义任务公开给方法的内容不包含真值节点 ID。
- 传统基线的语义解析固定为 `graph_only`：只读取地标名称/别名、节点坐标、合法上下车点和方向/邻近关系，不读取路牌、电线杆等道路特征实体，也不读取评估器真值。无法精确判断时仍使用记录过的合法候选或失败状态，不能把语义任务静默丢弃。
- Agent-readable 组使用 `RoadFeatureInputProtocol v1` 读取道路特征实体、侧别、朝向和配对节点关系。基线候选、Agent 候选和评估器真值分开记录；真值只用于评分，不进入规划输入。

## 3. 地图与道路表示

### 3.1 全局地图

首版主要地图为 100×100 规则网格，约 10,000 个节点。本实验只把 100×100 作为正式地图规模；更小地图不纳入方案对照或正式结果。

全局地图保留在模拟器中，不直接整张发送给 LLM。

### 3.2 首版最小道路特征

节点字段：

- `node_id`
- `x`、`y`
- `landmark_name`、`landmark_aliases`
- `legal_pickup`
- `legal_dropoff`

道路边字段：

- `from_node`、`to_node`
- `length_m`
- `base_speed_mps`
- `one_way`
- `congestion_level`（0/1/2）
- `signal_delay_sec`（无信号灯时为 0）

道路特征实体字段：

- `feature_id`
- `feature_type`（首版包含 `road_sign` 路牌和 `utility_pole` 电线杆）
- `node_id`
- `label`、`aliases`
- `side_of_road`、`orientation`
- `paired_node_id`（道路另一侧或相邻候选节点）
- `semantic_role`

道路特征实体不改变道路连通性和边权。图搜索基线可以继续只使用节点、道路边和合法性字段；Agent-readable 输入还读取这些实体的名称、侧别、朝向和候选节点关系。

首版不实现封闭路段、道路类型、车道数、复杂转向、实时信号相位和复杂有效期。

代码实现规则保持简单：`one_way=false` 时生成两个相反方向的边，`one_way=true` 时只生成 `from_node → to_node`；`congestion_level` 只取 0、1、2 三档，并由配置表映射到固定速度倍率；`signal_delay_sec=0` 表示无信号灯，非 0 表示固定等待时间，不模拟信号灯相位。

### 3.3 每轮场景

每轮随机生成：

- 地图随机种子；
- 道路单向属性和拥堵等级；
- 信号灯等待参数；
- 车辆起点；
- 订单上车点和下车点；
- 地标和合法上下车点标记。
- 路牌、电线杆等道路特征实体及其所在侧别、朝向和对应候选节点。

同一轮内所有方法使用同一份场景。地图、道路、信号灯和边界只在场景图中标注，不作为单独的地图优劣分数；道路特征是否可见由方法组的固定输入协议决定。

### 3.4 地图边界与场景最低条件

100×100 地图具有显式外边界，边界外没有节点和道路，路线不得越界，也不采用首尾相连的环绕规则。每轮场景至少保证：

- 一个或多个靠近边界的起点、上车点或下车点；
- 一批合法上车点和合法下车点，以及少量非法点用于检查；
- 至少一个可行的起点—上车点—下车点任务；
- 至少一个需要绕行的任务（由单向限制或拥堵造成）；
- 一定数量的地标及其别名，用于语义地点任务；
- 部分有信号灯或拥堵延迟的道路边；
- 少量不可达或超出局部输入范围的任务，用于记录失败和回退。

这些条件是场景生成的最低覆盖要求，不表示每轮必须包含完全相同的节点位置。场景生成器应检查条件，不满足时重新生成随机地图。

正式场景集按每个随机种子分别生成可行、边界、非法端点、绕行和不可达案例。不可达案例使用场景级的局部封闭边约束或局部输入截断记录，不修改基础地图的道路字段；后续路线输入包构建时必须显式传递该场景约束。

## 4. 统一路线输入包

### 4.1 生成规则

每个任务以车辆起点、指定上车点和指定下车点的最小包围区域为基础：

1. 四周扩展 10 个网格单元；
2. 提取区域内的全部节点和道路边；
3. 如果局部图不连通，每次再扩展 5 个单元；
4. 最多扩大 3 次；
5. 扩展在路线方法运行前完成，不能由某个待比较方法决定。

### 4.2 输入包内容

- 起点、上车点、下车点（精确任务为节点引用；语义任务为原始地点文本和候选解析结果）；
- 节点坐标和地标字段；
- 合法上车/下车标记；
- 道路边连接、长度、速度和单向属性；
- 拥堵等级和信号灯等待时间；
- 路牌、电线杆等道路特征实体、别名、道路侧别、朝向和对应节点关系（仅 Agent-readable 输入条件可见；纯 LLM R3 使用图结构投影，不发送这些字段）；
- 地图版本、道路状态版本和随机种子；
- 场景级封闭边或局部输入截断约束（仅在不可达/范围外案例中使用）；
- 局部图节点数、边数和序列化 token 数；
- 语义任务的原始 `pickup_text`/`dropoff_text`、解析器版本、候选节点、解析状态和可见性；评估器真值只保存在独立评估记录中。

### 4.3 公平性

精确节点任务中，Dijkstra、A*、纯 LLM 和 Agent 工作流接收同一份解析后的输入包。语义任务中，所有方法接收同一份原始语义输入包和图数据，但地点解析候选属于方法输出；候选生成后统一交给同一套路线规划接口、验证器和评估器。这样比较的是语义解析与工作流差异，而不是把评估器真值直接发给某个方法。

全局 100×100 地图上的 Dijkstra 结果可以另外计算，作为理论最短路参考，不与局部输入下的主比较混在一起。

## 5. 路线方法与对照组

### R0：全图参考路线

使用全局道路图运行 Dijkstra，计算理论最短距离/时间参考。R0 不作为主要方法排名，只用于检查局部输入包是否截断了可行路线，并计算路线差距。

### R1：局部图 Dijkstra

在统一 `RouteInputPackage` 上运行 Dijkstra。精确任务直接使用输入节点；语义任务先调用固定的 `graph_only` 解析器，再输出一条最短路线、记录过的回退路线或结构化不可行结果。语义解析失败不等同于路线算法失败。

### R2：局部图 A*

在同一输入包上运行 A*，并使用与 R1 相同的 `graph_only` 语义解析规则。启发式函数使用节点到目标点的几何距离，保证不改变道路约束。记录搜索节点数、路线时间和搜索耗时。

### R3：纯 LLM 路线规划

使用 DeepSeek V4 Flash API。输入为与其他方法相同的路线输入包，直接要求模型输出路线节点/道路边序列和相关估计值。输出必须经过统一解析、路线合法性检查和成本评估。

LLM 不得直接读取真实答案节点 ID，也不得绕过路线检查。解析失败、超时或路线非法均保留记录。

**2026-10-18 用户确认的本轮纯 LLM 输入口径：**只向模型提供普通路网拓扑、方向、边界、合法上下车标记和普通地标名称/别名；不提供路牌、电线杆、道路侧别、朝向、配对节点等 Agent-readable 道路特征字段。本轮用逐节点有向出口掩码明确每个可走方向，并要求模型逐步核对；模型路线仍由 LLM 自行生成，程序只做事后统一校验，不调用 Dijkstra/A* 限制、修复或替代模型路线。该输入和提示只能降低错误概率，不能保证原始模型提议零违规。v7 归档的提示实际序列化了 `roadside_features` 字段，因此应保留为旧版诊断结果，不与本口径的纯图结构输入结果直接合并。

### R4：Agent 路线检索与 Agent-readable 地图

R4 的两项重点是**地图表示范式**和**路线检索流程**。同一底层 `RouteInputPackage` 经确定性适配器转换成版本化 `RoadFeatureInputProtocol v1`（实体—特征—关系—约束—语义索引）；本地 Hugging Face 模型把自然语言上下车目标解析成结构化 `RouteIntent`；候选 ID 只能从协议白名单中选择；协议按查询返回相关特征和局部路网，DeepSeek Flash 据此生成路线；独立程序验证路线并以结构化错误反馈，最多规划三次。路线 API 输入必须明确表达当前节点的合法有向出边、边界、端点与统一通行时间；编码还需在 100×100 任务上完成 token 规模预检。完整流程图和输出字段见 [R4 设计与结构图](../../docs/route-layer-r4-agent-workflow-design-2026-10-16.md)。

R4 只处理一个车辆—订单路线任务，不包含全局车辆—订单分配、下一订单衔接或调度层优化器。R4 与 R3 复用种子 0–9 的地图、道路状态、任务、评估器、能耗模型和费用口径。R4 主组固定使用 Qwen3-4B-Instruct-2507 的本地 MLX 4-bit 量化制品作为地点/道路特征意图解析器：基础模型 revision 为 `cdbee75f17c01a7cc42f958dc650907174af0554`，量化仓库 `mlx-community/Qwen3-4B-Instruct-2507-4bit` revision 为 `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`；使用 DeepSeek Flash 作为路线生成模型，并在每次运行时记录请求和响应实际模型标识。Qwen 只作单次结构化解析，不做微调，不调用托管推理 API，也不构建跨场景知识库。模型卡及本地推理限制见第 10.1 节。

#### R4 固定运行规则

1. 精确任务按输入端点运行；语义任务向模型提供原始地点文本，不提供评估器保存的真实答案节点。
2. 适配器为同一地图快照生成并保存完整协议 JSON。协议保留 `map_id`、地图/道路状态版本、单位、稳定实体 ID 和来源时间；节点/有向道路、地标、路牌、电线杆、合法上下车候选，以及侧别、朝向、别名和配对关系按统一字段表达。运行时只按查询向模型提供相关语义索引和局部道路子图，避免反复传入 100×100 全图。
3. Qwen 仅输出 `RouteIntent` JSON：任务地点的地标/特征引用、相对关系、侧别/朝向、候选实体引用、路线偏好、证据引用、置信度与解析状态。程序校验 ID 白名单、schema 和候选合法性；未解析或歧义任务保留为解析失败，不进入路线 API。
4. DeepSeek Flash 只接收局部有向道路子图与已校验候选并执行路径搜索，输出紧凑有向路线 JSON，不返回解释、思维链或其他无关内容。每个可行方向必须可逐边核验；未提供的反向边不得推断为可通行。正式编码需同时满足 100×100 输入 token 预算和可审计的方向/边成本精度。路线生成、端点解析、验证反馈分别留档。
5. 每任务最多三次路线规划：初次一次，验证失败后最多两次重规划。默认不做网络重试，避免无意重复收费；如单独启用，必须作为 API 重试计数记录，不算 Agent 重规划。
6. 验证反馈只包括错误类型、违规步号、边/方向不合法、越界、端点非法、封闭边、不可达等信息；不反馈评估器真实节点 ID。重规划请求把反馈作为原始用户 JSON 对象顶层的 `r4_validation_feedback` 字段，并由系统提示声明它是程序校验信息、不是地图事实；不得在 JSON 对象闭合后追加文本。主实验不调用 Dijkstra/A* 约束、修复或替代模型路线。
7. 合法路线由相同程序按合法性、总行驶时间、距离、电耗顺序筛选。没有合法路线时保留失败分类；若收到非法路线序列，保留其违规轨迹并仅把路线能耗作为“提议估算”单独记录。

每次意图解析和路线尝试都记录模型与 revision、schema/prompt 版本、输入 hash、原始结构化输出、候选点、道路特征证据、token/本地输入输出长度、推理时延、API 费用、验证状态、反馈内容及重规划序号。可视化结构与传统组一致：根索引 → 10 个种子 → 原地图和订单/正式场景 → 方法结果 → 单任务轨迹回放。回放需展示协议摘要、Qwen 意图、证据引用、每轮路线、违规步、反馈、最终状态、电耗和成本。

#### 5.1 道路特征输入协议与对照

路线层固定使用 `RoadFeatureInputProtocol v1`，JSON 中包含 `context`、`route_query`、`entities`、`features`、`relations`、`constraints`、`semantic_index` 和 `output_contract`。节点与有向边提供道路拓扑；地标、路牌、电线杆作为具名实体；道路侧别、朝向、别名、通行状态等作为特征；连接、邻近、所在侧、配对候选等作为关系；边界、单行、封闭边和上下车规则作为约束。具体字段由代码数据模型和 R4 设计文档共同冻结。

语义索引暴露的是本次输入内可检索对象及其候选实体，不是评估器真值。真实答案节点仅用于实验后评分。协议不含真实图像感知、微调、Agent 自建跨场景知识库或 VLM；道路特征是已知地图事实，由适配器转换为模型可读取的范式。

R4 增加两项小消融，主实验仍是 R0–R2、R3、R4：

| 消融 | 改动项 | 固定项 | 目的 |
|---|---|---|---|
| R4-A 地图输入消融 | 将 `RoadFeatureInputProtocol v1` 换为 graph-only，不提供路牌/电线杆语义和侧别关系 | Qwen revision、DeepSeek、任务、验证器、反馈次数、成本口径 | 检查可读道路特征范式的作用 |
| R4-B 反馈消融 | 关闭验证反馈重规划，仅保留一次 DeepSeek 路线提议 | 完整道路协议、Qwen、任务、验证器和费用口径 | 检查新路线检索反馈流程的作用 |

三种道路特征场景仍固定为：路牌近侧定位、双向道路另一侧修正、电线杆/路牌语义锚点。传统 graph-only 组仍需解析语义目标并输出合法候选，不得因未读取道路特征而直接判失败；预期绕行差异只能在路线实际生成后评分。

### 5.2 消融实验二：Agent + 传统算法 vs Agent + LLM

保持 Agent 状态读取、地点映射、规则检查、反馈重规划、输入包、输出 schema 和验证器不变，只替换路线生成模块：

- **Agent + Dijkstra**；
- **Agent + A***；
- **Agent + DeepSeek V4 Flash**。

该实验检验传统算法和 LLM 是否分别适合作为 Agent 的路线工具。传统算法或纯 LLM 如果在某些指标上更好，应保留其优势组件，不预设 Agent+LLM 必然最优。

### 5.3 主要对照关系

主路线方法仍包括局部图 Dijkstra、局部图 A*、纯 LLM 和完整 Agent 工作流。两组消融用于解释完整工作流的效果来源，不把所有变量同时改变。

## 6. 两类路线任务

### 6.1 精确节点任务

输入明确的上车点和下车点节点 ID。该任务主要测量路线搜索、道路约束处理和成本计算能力。

### 6.2 语义地点任务

输入乘客地点描述，例如“某个牌子下面”“体育馆东门”。所有方法收到相同的原话、局部道路图和地标字段，但不直接收到正确节点 ID；道路特征实体是否可见由固定的对照协议决定。传统方法使用固定的图规则解析器：匹配地标名称/别名、方向、邻近和合法性；道路特征文本不匹配实体时使用记录过的几何/合法候选或结构化失败。Agent/LLM 方法可额外读取 `RoadFeatureInputProtocol v1`，但也必须返回候选节点和解析状态。

正确节点由评估器保存。方法需要输出解析后的节点或道路边，再生成路线。解析出的节点可以与真值不同；只要路线满足图约束，仍是有效路线，端点精确匹配作为单独评分指标。

该任务测量：

- 地点语义解析；
- 地标到道路节点映射；
- 合法上车/下车点判断；
- 语义歧义和解析失败处理。
- 图规则基线与 Agent-readable 候选之间的节点偏差、道路侧匹配、绕行距离和掉头代理指标。

## 7. 路线输出

路线数量不强制一致。每条输出路线都转换成统一结构：

- 路线节点/道路边序列；
- 起点、上车点和下车点；
- 路线来源；
- 是否可达；
- 是否经过合法上车/下车点；
- 路线距离和时间；
- 信号灯和拥堵影响；
- 预计电耗；
- 生成、检查和总决策时间；
- 解析错误、验证错误和回退信息。
- `semantic_resolution`：解析器、可见性、解析状态、候选节点、回退策略和是否读取道路特征；评估器真值只出现在评估记录，不出现在规划输入。

每个任务记录：

- `route_output_count`
- `valid_route_count`
- `invalid_route_count`
- `route_generation_timeout`
- 最佳有效路线；
- 平均有效路线；
- 首条路线。

## 8. 交通、时间和电耗计算

路线方法只输出路线。统一仿真评估器根据相同的道路状态计算：

- 基础行驶时间；
- 简单信号灯等待时间；
- 简单拥堵额外时间；
- 总行驶时间；
- 停车次数；
- 行驶电耗；
- 信号灯等待电耗；
- 拥堵等级带来的额外电耗；
- 总电耗。

首版采用简单分段模型：有效速度由基础速度乘以拥堵倍率得到，总时间为路段行驶时间加固定信号灯等待时间；电耗由行驶距离基础电耗加信号灯等待和拥堵等级对应的简单附加电耗得到。所有方法共享同一组参数。该结果是仿真估计，不等同于真实车辆测量。

### 9.4 失败与鲁棒性

- JSON/结构化输出失败；
- 无法解析路线；
- 路线非法；
- 对方向序列生成的路线，即使在首个违规动作处判定失败，也要保留完整模型提议序列，按地图重放合法前缀，并标注全部违规步的步号、起终节点、方向和约束类型；首次违规之后的虚线路径须注明仅代表模型提议，不表示可通行或已执行；
- 将“模型是否返回响应”“是否返回路线步骤”“路线是否合法”分开记录。模型明确返回无路线、端点解析失败，或响应无法解析时，不得把路线违规数为 0 写成 API 未返回或路线成功；无可恢复路线步骤时，耗电记为“不适用/未估算”，不把缺失值解释成 0 kWh；
- 对包含非法移动的完整路线提议，按统一能耗模型分别估算完整提议路线和首个违规动作前的合法前缀，并在字段及可视化中标明这是基于模型提议的假设估算、不是实际车辆耗电；无法对应到地图有向边的移动须标出采用反向道路属性或地图中位路段属性估算的数量。此估算不得进入有效路线能耗和总费用比较；
- 对截断响应，只记录可恢复的完整方向段及其部分路线估算，明确标记“不完整”；
- 指定点无法抵达；
- 超时；
- LLM 重试次数；
- Agent 重规划次数；
- 回退函数或回退路线使用次数。

**R3 v8 已完成结果（2026-10-18）：**在 seed 0–9 的 150 个任务上共发出 150 次纯 LLM 路线请求，全部收到响应、没有请求层 API 错误；合法路线为 0/150。模型返回了 19 条路线序列，均含逆单行移动，共 124 个违规步；没有越界移动。其余 131 条响应没有可恢复路线步骤。传统组同任务核对显示，130 个可行任务的三种传统算法均能找到路线；另 20 个正式场景按设计为非法端点或不可达。19 条提议路线的完整假设能耗估算合计 30.84645 kWh，首次违规前合法前缀估算合计 6.15930 kWh；这不是实车耗电，且未计入有效路线成本。实验与逐任务回放见 [`v8 运行记录`](../../docs/route-layer-pure-llm-run-2026-10-18-v8.md) 和 `outputs/route_layer/pure_llm_experiment_v8/index.html`。本结果说明 graph-only 输入下仍未得到合法路线，不能据此宣称纯 LLM 路线效果或 Agent 优势。

### 10.1 R4 的 Hugging Face 本地意图模型（2026-10-18，方案待验证）

R4 固定采用 Hugging Face `mlx-community/Qwen3-4B-Instruct-2507-4bit` 作为**自然语言地点/道路特征意图解析器**，量化制品 revision 固定为 [`50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`](https://huggingface.co/mlx-community/Qwen3-4B-Instruct-2507-4bit/tree/50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b)，其基础模型为 [`Qwen/Qwen3-4B-Instruct-2507`](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507/tree/cdbee75f17c01a7cc42f958dc650907174af0554)。量化仓库模型卡标注 4-bit、约 2.28 GiB、Apache-2.0；使用 MLX 本地推理。模型读取原始地点描述和 `RoadFeatureInputProtocol v1` 查询结果，只返回 `RouteIntent` JSON 与所引用的实体/特征 ID；本段记载的 DeepSeek Flash 路线候选生成是 2026-10-18 历史方案，已由 2026-10-22 当前执行补充更新为 Codex CLI 分步路线生成。Qwen 不做全图路线搜索，不微调，不调用 Hugging Face 托管推理 API，也不写入跨场景知识库。

基础模型卡将 Qwen3-4B-Instruct-2507 标为 Apache-2.0、4B 参数指令模型；量化仓库提供 MLX 4-bit 制品并标为 Apache-2.0。上述信息只支持选型，不代表道路特征解析或路线规划效果。固定权重现已下载并按缓存 SHA-256 校验，MLX-LM 0.31.3 在临时 venv 中加载成功。本地 Qwen 在两次 8×8 seed 0 语义道路特征烟雾中均通过意图 schema、候选白名单、协议引用和真值隔离门禁。第一次 DeepSeek 路线请求（921/82 输入/输出 token）返回越界路线；第二次将路线输入改为显式有向邻接后，输入/输出 token 为 4,381/128，输出触及 128 token 上限并截断，解析失败。第二次可恢复的 12 步提议没有非法移动，但未到达上下车点；假设能耗估算 0.223 kWh，不能作为有效路线成本。第二次 API 费约 0.013527 CNY。对 100×100 同种子任务的离线尺寸预检显示显式 JSON 邻接输入中位 600,909 字节，粗略 token 外推过高，不适合直接启动正式批次。脚本后续烟雾上限已改为 512 token，尚未实际调用验证。详见 [R4 烟雾检查记录](../../docs/route-layer-r4-smoke-test-2026-10-18.md)、`outputs/route_layer/r4_smoke_v1/seed0_semantic_road_feature.json` 和 `outputs/route_layer/r4_smoke_v5/seed0_semantic_road_feature.json`。正式 R4 多种子实验未启动；需先完成 100×100 紧凑输入设计、费用预算及新的端到端烟雾。

### 10.2 R4 有向路线硬约束与逐步自检（2026-10-19，离线实现待 API 验证）

R4 将地图表达为 `directional-cost-grid-v1` 紧凑有向网格，并随结构化自然语言地图指南解释节点坐标、E/W/N/S 出边槽、`.` 禁止通行语义、反向单行规则、成本编码和边界。路线输出采用从局部 `RouteInputPackage` 实际有向边集合生成的 DeepSeek strict function tool schema；每个槽码只对应一个具体起点与方向，反向单行边和不存在的出边不会进入可输出集合。真实 DeepSeek 客户端缺少或使用错配约束时会在请求前停止，strict schema 请求不做网络重试。

模型一次提交完整路线，并用紧凑 `step_check_sequence` 对每条边输出一个 `1`，表示模型声称已逐步检查该有向边、连续性与端点顺序。此字段是模型的自检记录，不是正确性的证明；不要求模型输出长篇思维链。离线归一化器拒绝自检字符数与边数不一致的路线。独立本地校验器再次检查每一步有向边、连续性、起点、先上车后下车、边界及末节点必须等于下车点。只有两种自检记录完整、模型声明字段匹配且独立校验全部通过时，路线才能标记为有效；否则保留模型提议和逐步审计，结果记为失败，不使用传统算法生成或修复路线。因而实验口径是“零违规路线被接纳”，不是预先保证 LLM 永远不会提出非法或不完整路线。

烟雾回放在每个步骤展示模型声明、本地有向边/连续性/端点顺序复核及是否接纳；旧历史记录若未保存自检字段，会明确标为无该项历史数据。离线测试已覆盖自检码缺失或步数不符、真实出边与反向边、集合外槽码、断开边序列拒绝、连续性/端点验证和回放字段。全套测试 72 项通过。2026-10-19 已按一次请求、512 输出 token、零重试完成 v11 API 验证：DeepSeek 接受 strict 有向边 schema，返回 2,168/116 输入/输出 token、费用估算 0.006852 CNY，但模型返回 `failed` 且未提交路线；事后 BFS 显示任务可达，因此 smoke 未通过路线成功门槛。此次验证不能证明新 schema 下路线合法性或自检有效。正式 R4 十种子实验未启动；需先重新评估失败原因与是否进行下一次单次验证，不能自动重试或批量运行。该设计不改变 R3 v8 已完成结果。详见 [R4 烟雾记录](../../docs/route-layer-r4-smoke-test-2026-10-18.md)。

### 10.3 R4 当前分步 Codex 执行方法（2026-10-22）

R4 沿用 `directional-cost-grid-step-v1` 紧凑地图和 `RoadFeatureInputProtocol v1`。本地 Qwen 先根据原始地点表达、白名单特征/地标记录解析候选端点；只把经白名单/合法候选校验的相关特征片段和 Qwen 意图连同紧凑有向地图交给 Codex。评估器真值不进入输入。Codex 每次只提议一个方向并返回限定 JSON 对象；请求禁用工具、零网络重试。

每一步 schema 的方向枚举由当前节点真实有向出边、访问状态、先上车后下车规则、剩余可达性和路线动作总预算计算。返回后本地确定性程序再次核验有向边、连续性、边界、重复访问、端点顺序及剩余可达性；仅校验通过才推进路线状态。模型自检结构化留档，作为声明与本地事实的差异审计，不替代程序结论。违法提议不会被执行或接纳、不会用传统路线算法兜底；保留失败提议、拒绝原因和假设耗电估计。没有完整合法路线时，实际路线耗电保持未评估。

`max_route_actions` 控制单条路线最多动作数；`max_api_calls` 控制当前运行允许的模型请求数，两者分开记录。请求数先达到上限而未到下车点时，记录 `request_limit_exhausted`、有效前缀和当前节点，不能记为完成路线或作为正式完整路线样本。R4 对照与纯 LLM 方法的模型后端统一使用 Codex CLI；后端费率估值、CLI 实际 usage 和账户实际扣费分别报告，账户实际扣费若无 CLI 证据则标为未知。
