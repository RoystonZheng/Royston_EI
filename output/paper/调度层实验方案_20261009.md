# 调度层实验方案

日期：2026-10-09  
状态：正式实验设计草案。  
前置条件：路线层已经为车辆—订单组合生成统一路线候选和成本记录。  
实验规模：10 辆车、1 小时、每轮 100 个动态订单。

## 1. 实验目标

调度层研究：在已有服务承诺和路线成本的约束下，车辆 Agent 如何提出下一订单候选，情境函数如何减少无效候选，LLM 如何提供候选反馈，数学优化器如何完成最终车辆—订单分配。

主要验证：

1. Agent 候选筛选是否减少无效候选和调度计算量；
2. 当前订单完成后的下一订单衔接是否提高服务结果；
3. LLM 生成的情境函数是否比固定/人工函数更适应订单密度和车辆状态变化；
4. LLM 候选反馈是否能在数学优化器前改善候选评价；
5. 全局优化器是否比逐订单贪心减少冲突、积压和等待；
6. 各方法的调度时间、API/算力成本和车辆运行成本。

调度层不重新研究地图路线算法。所有方法使用同一地图、订单、车辆状态和路线层候选表。

## 2. 固定实验场景

### 2.1 地图和道路

- 使用路线层生成的 100×100 离散道路图；
- 道路节点和道路边字段保持路线层的最小版本；
- 1 小时内道路状态固定；
- 不模拟封闭路段、动态拥堵变化或道路变化导致的换车；
- 单向、拥堵等级、信号灯等待在本轮固定；
- 地图边界为硬约束，车辆和路线不得越界。

### 2.2 车辆

- 车辆数固定为 10；
- 每辆车同一时刻最多服务一名乘客；
- 车辆状态包括空闲、前往上车点、已到达等待、载客中和异常；
- 当前订单承诺一旦生效，不能被新订单随意取消；
- 当前订单执行期间每辆车最多预留一笔下一订单。

### 2.3 订单

- 仿真时间为 1 小时；
- 每轮固定生成 100 个订单；
- 到达时间不预先设置时段权重；为 100 个订单生成随机间隔并归一到 1 小时后排序，允许自然出现局部高密度、低密度和空档；
- 上车点从场景预设的 3 个合法空间热点中随机生成，热点分别标记为高、中、低密度；热点位置和范围在场景开始时固定，同一随机种子下所有方法共享；
- 高密度热点面积最小、中密度热点面积居中、低密度热点面积最大；三个热点被抽中的概率相同，热点内部再随机选择合法上车点，以面积差异形成单位面积密度差异；
- 下车点从全图合法下车点均匀随机生成；
- 同一随机种子下所有方法使用完全相同的订单到达序列和起终点；
- 不在调度层改变地图或道路状态。

订单生成后再按固定的 **5 分钟时间窗口**统计实际时间密度，共 12 个窗口；空间密度根据预设热点和已生成的订单位置统计。结果汇总时，窗口权重取该窗口订单数占本轮 100 个订单的比例。热点密度标签仅用于结果分层；运行中的 Agent 可根据当时已经到达的订单计算局部订单密度，但不能读取未来订单。

## 3. 调度事件

每次发生以下事件时，生成状态快照并执行一轮调度：

1. 新订单到达；
2. 当前订单完成；
3. 已预留下一订单被取消；
4. 乘客到达后未按规定时间上车，订单取消。

道路状态变化不作为首版调度事件。

每一轮优化器重新考虑：

- 全部未服务订单；
- 当前车辆完成现有任务后可以衔接的下一订单；
- 当前已有服务承诺和车辆占用状态。

## 4. 订单状态机与取消规则

```text
待服务
  → 已分配
  → 车辆接驾中
  → 车辆已到达上车点
  → 乘客已上车
  → 载客完成

车辆到达后，乘客等待超过“到达后上车等待阈值”
  → 乘客未按时上车取消
```

需要区分两个时间：

1. **乘客接驾最大等待时间**：从订单产生到车辆到达上车点，是调度筛选硬约束；
2. **到达后上车等待时间**：车辆到达上车点后等待乘客，是订单取消条件。

订单取消后：

- 记录取消原因；
- 不计入运力不足未服务；
- 释放车辆；
- 车辆重新进入调度池；
- 取消事件触发下一轮调度。

本实验将乘客接驾最大等待时间固定为 **300 秒（5 分钟）**。所有方法、轮次和订单都使用同一数值。车辆到达上车点后的乘客上车等待阈值另行设置，不与该值混用。

车辆到达上车点后，乘客最多等待 **180 秒（3 分钟）**；超过该时间仍未上车，则订单取消并释放车辆。

每轮订单中随机固定 **5%** 为“乘客未按时上车”订单。此标记在场景生成阶段确定，并在同一随机种子下对所有方法保持一致；其余订单在车辆到达上车点后立即上车。

## 5. 统一输入和输出

### 5.1 `DispatchInputPackage`

所有调度方法接收完全相同的输入：

- 当前仿真时间和事件类型；
- 10 辆车的状态、位置、当前订单和承诺；
- 全部未服务订单及等待时间；
- 路线层生成的完整车辆—订单候选表；
- 候选路线、预计接驾/送达时间、空驶距离和电耗；
- 当前固定最大等待时间；
- 一对一服务规则；
- 每辆车最多预留一笔下一订单的规则；
- 目标优先级版本；
- 输出 schema 版本。

统一输入不包含任何方法预先筛选后的候选结果。候选筛选、回退和 LLM 反馈是各方法内部步骤。

### 5.2 `DispatchDecisionPackage`

所有方法都必须输出相同结构：

- 方法名称和版本；
- 选中的车辆—订单分配；
- 每辆车是否预留下一订单；
- 未服务订单和积压订单；
- 每个分配的预计接驾/送达时间；
- 当前订单承诺检查结果；
- 优化器/LLM 状态、超时状态和回退状态；
- 冲突、失败和未服务原因；
- 计算时间、调用次数、token 和金钱成本。

纯 LLM、贪心规则、Agent+优化器和 Agent+LLM反馈+优化器都先转换成该结构，再由同一个验证器检查。

## 6. 情境函数与候选筛选

### 6.1 输入特征

首版使用 7 个状态特征：

1. 局部订单密度；
2. 局部空闲车辆密度；
3. 需求/供给比；
4. 当前订单承诺余量；
5. 候选订单预计接驾时间；
6. 当前时间段；
7. 当前车辆状态。

### 6.2 函数形式

首版固定为 `linear_clip`：

```text
threshold = clip(
  base
  + w1·order_density
  + w2·idle_vehicle_density
  + w3·demand_supply_ratio
  + w4·commitment_slack
  + w5·candidate_eta
  + w6·time_context
  + w7·vehicle_state,
  min_threshold,
  max_threshold
)
```

函数输出一个候选接驾时间阈值。数学优化器限定阈值范围，并保证阈值不能破坏最大等待时间和已有服务承诺。

### 6.3 函数生成和复用

- 固定阈值函数：作为简单对照；
- 人工参数的 `linear_clip`：作为规则自适应对照；
- LLM 参数的 `linear_clip`：作为完整函数方案；
- LLM 只输出固定格式的参数，不直接执行任意代码；
- 数学优化器监控动态特征；
- 所有动态特征仍在函数适用范围内时复用旧函数；
- 任一关键特征越出适用范围时，触发 LLM 更新函数；
- 函数生成、函数监控和函数运行时间分开记录。

### 6.4 候选为空时的回退

1. 先按当前函数阈值筛选；
2. 如果某 Agent 没有候选，则扩大到仍满足最大等待时间的全部候选；
3. 如果仍为空，输出“暂无可行候选”；
4. 本轮不临时让 LLM 重写函数；
5. 记录回退原因和回退次数。

## 7. 调度方法与对照组

### D0：逐订单最近可行车辆贪心规则

这是简单基线，必须在方案中明确：

1. 按最早服务截止时间处理订单，即订单到达时间加最大等待时间；
2. 删除路线不可达、超过最大等待时间或影响当前承诺的车辆；
3. 在剩余车辆中选择预计接驾时间最短的车辆；
4. 接驾时间相同则比较空驶距离；
5. 仍相同则按订单编号/车辆编号固定排序；
6. 已分配车辆不回退、不全局换车；
7. 无可行车辆则记录为未服务或积压。

D0 不使用全局数学优化器、LLM 函数或 LLM 反馈，但读取统一输入和输出结构。

### D1：集中式数学优化器

优化器直接读取完整车辆—订单候选表，不经过 Agent 情境筛选和 LLM 反馈。用于检验全局协调本身相对贪心规则的作用。

### D2：Agent + 数学优化器

车辆 Agent 根据固定或人工参数的情境函数筛选候选，输出候选成本和下一订单衔接状态；数学优化器完成最终分配。

### D3：Agent + LLM 情境函数 + 数学优化器

LLM 低频生成 `linear_clip` 参数，数学优化器监控和限制函数范围；Agent 使用函数筛选候选，优化器最终分配。

### D4：Agent + LLM 情境函数 + LLM 候选反馈 + 数学优化器

完整方法：

1. Agent 按情境函数筛选候选；
2. 程序检查路线、最大等待和当前承诺；
3. LLM 只读取通过硬约束检查的候选；
4. LLM 按候选逐条输出保留判断、时间/成本评价、风险和理由；
5. 数学优化器读取结构化反馈并完成最终分配。

### D5：纯 LLM 派单

纯 LLM 读取与其他方法相同的 `DispatchInputPackage`，直接输出 `DispatchDecisionPackage`。它不使用 Agent 候选筛选和数学优化器，但输出仍由统一验证器检查硬约束。

## 8. 数学优化器约束和目标

### 8.1 硬约束

- 每个订单最多分配给一辆车；
- 每辆车同一时刻最多载一名乘客；
- 每辆车最多预留一笔下一订单；
- 当前订单承诺不能被新订单破坏；
- 订单产生到车辆到达上车点的等待不得超过固定最大等待时间；
- 路线必须可达且不越过地图边界；
- 车辆任务时间不能重叠；
- 选中的候选必须通过统一路线和上下车点验证。

### 8.2 优化优先级

1. 保持已有服务承诺；
2. 最大化可服务订单数；
3. 最小化已服务订单平均等待时间；
4. 再比较空驶距离、计算时间、电耗和金钱成本；
5. 未服务订单保留为积压并记录等待时长和原因。

## 9. 调度层指标

### 9.1 服务结果

- 订单服务率；
- 未服务订单数；
- 积压订单数及持续时间；
- 已服务订单平均等待时间；
- P95 等待时间；
- 最大等待时间；
- 当前订单承诺违反次数；
- 下一订单衔接成功率；
- 乘客未按时上车取消数；
- 取消与运力不足未服务的分类计数。

### 9.2 Agent 和函数效果

- 每轮候选总数；
- 函数筛选后候选数；
- 候选压缩率；
- 无候选次数；
- 回退次数；
- 函数复用次数；
- 函数更新次数；
- 函数越界触发次数；
- LLM 反馈后候选保留率；
- LLM 判断与最终优化选择的一致率。

### 9.3 计算和金钱成本

- Agent 状态判断时间；
- 候选函数运行时间；
- 函数监控时间；
- LLM 函数生成时间；
- LLM 候选反馈时间；
- 数学优化器求解时间；
- 每轮总调度响应时间及 P50/P95；
- LLM/API 调用次数、token 和 API 费用；
- 算力时间和算力费用；
- 车辆电耗和电费；
- 条件一致时的总金钱成本。

## 10. 重复实验与控制变量

- 每轮 10 辆车、100 个订单、1 小时；正式实验使用 10 个随机种子；
- 订单到达时间随机生成，不预先设置高峰权重；生成后按统计窗口计算实际密度；
- 上车点从场景预设热点内的合法上车点随机生成；热点位置、范围和抽样规则由场景生成器统一提供；
- 下车点从合法下车点均匀生成；
- 同一随机种子下所有方法共享同一订单流、车辆初始状态、路线候选表和最大等待时间；
- 所有方法使用同一输入输出 schema、硬约束验证器和统计窗口；
- 首轮 LLM 使用 DeepSeek V4 Flash API；具体 `model_id` 从运行配置读取，并在日志中记录实际模型标识、版本、token、延迟、失败和费用；
- Hugging Face 托管模型作为后续模型对比，不与首轮调度机制对比混在一起；
- 所有未服务、取消、超时和失败结果都保留。

## 11. 实施顺序

1. 固定 10 辆车、1 小时、100 个订单的场景生成器；
2. 生成订单到达时间和高/中/低密度上车区域；
3. 接入路线层完整候选表；
4. 实现订单状态机和两类等待计时；
5. 实现 D0 贪心基线；
6. 实现 D1 集中式优化器；
7. 实现固定阈值和人工 `linear_clip`；
8. 接入 LLM 生成函数参数；
9. 实现 Agent 候选输出和回退；
10. 接入 LLM 逐候选反馈；
11. 实现 D5 纯 LLM 输出和统一验证；
12. 运行多轮随机订单流；
13. 输出服务、等待、衔接、积压、计算和金钱成本结果；
14. 根据结果决定是否加入更多模型或函数形式。

## 12. 教师汇报时的简短表述

调度层在 100×100 固定道路图上设置 10 辆车、1 小时和 100 个动态订单。订单到达时间随机变化，上车点从场景预设热点内的合法点随机生成，下车点从全图合法点随机生成。每次新订单到达、当前订单完成或订单取消时，系统重新考虑全部未服务订单和可衔接下一订单。所有方法读取相同的完整车辆—订单候选表，并输出相同结构的派单结果。对比逐订单最近可行车辆、集中式优化器、Agent+优化器、Agent+LLM情境函数+优化器、Agent+LLM反馈+优化器和纯 LLM 派单。最大等待时间是统一硬约束，车辆到达后乘客未按时上车则按另一计时规则取消。主要比较服务率、等待、积压、下一单衔接、计算时间、API/算力费用和车辆电费。

## 14. 数据驱动 Agent—Codex—优化器组合更新（2026-10-22）

本节记录当前 NYC TLC 共享输入支线，覆盖早期 10 辆车/100 订单/100×100 合成图设计的不同数据条件；两种场景不得混合汇总。

- 当前组合方法设计、消融、NN 标签边界和分阶段门见 [多 Agent、Codex、数学优化器与神经网络实验设计](../../docs/dispatch-layer-hybrid-agent-codex-nn-design-2026-10-22.md)。
- D6 的核心流程为 Vehicle Agent 生成当前可行候选 → Codex CLI 每次模拟最多一次输出受限 `linear_clip` 参数 → 集中式优化器全局匹配 → 统一 validator 检查。LLM 不直接派单、不读未来订单、不改硬约束；零重试，失败回退到固定策略。
- 首轮 C3 seed 0 的 D6 集成 pilot 已完成；C4/F1/seed 0 的 D6/D7 容量保护配对 pilot 也已完成，报告见 [配对 pilot](../../outputs/dispatch_layer/nyc_tlc_hvfhv_2024/three_method_benchmark_v1/results/hybrid_agent_codex_capacity_shield_v1/C4_manhattan_790_order_five_minute_load_sweep/F1/capacity_shield_pilot_report.md)。这些单 seed 运行只验证组合链路、机制触发与记账，不构成正式性能结论。
- D7 是 Agent+Codex+最大匹配容量保护；它在 C4/F1 第 3 轮将筛选后的最大匹配从 4 条恢复到完整可行图的 5 条。神经网络候选排序顺延为 D8，尚未实现。当前 TLC 数据不含未服务需求及真实车队轨迹；以 D1 优化器输出训练只能称为优化器模仿，不是真实决策标签。
- 正式批次需使用多个独立 TLC 时间窗口及 F1/F2/F4 车队配置，对 D2/D6/D7 做配对比较。每个输入窗口由 D7 产生一次 Codex 策略响应，再向 D6 回放相同 prompt 与响应以控制模型变动并节省调用；固定窗口只更换 seed 不算独立需求样本。D0/D1/D5 仅在场景指纹、数据哈希和版本一致时复用。
