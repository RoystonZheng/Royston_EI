# 我对这 110篇论文的理解

## 1. [RideSkill](https://arxiv.org/html/2609.02250v2)
**这篇讲了什么**
这篇做的是拼车调度和空车调位。它先让 LLM 生成不同的调度策略，通过仿真反馈反复改，留下能用的策略。真正运行时，由组合器给车辆选择策略，重定位器决定空车往哪里走，不需要每次派单都等 LLM 回答。我比较认可把策略提前准备好、运行时重复使用的方式。
**我觉得不足的地方**
公平性主要看车辆之间的工作量差异，但是存在不同区域的乘客会不会一直等不到车；自然语言目标的测试还不够让我放心，模糊、互相矛盾、恶意或者缺少业务条件的要求能不能处理，还需要确认。论文里更换底层 LLM 后效果也有差异。
**我想引用什么**
我会参考它的分层结构、可复用策略和离线生成思路，减少在线调用 LLM 的次数。乘客公平、含糊目标的处理和生成结果检查，也是我想继续考虑的部分。

## 2. [AIFP：Adaptive Iterative Feedback Prompting for Obstacle-Aware Path Planning via LLMs](https://openreview.net/pdf?id=M4rLudFbT2)
**这篇讲了什么**
它让 LLM 给机器人规划接下来的几个位置，再检查这些位置之间的路线会不会碰到障碍。能走就往前走一段，不能走就把碰撞反馈放回提示词，让模型重新规划。它不是一次生成整条路线就不管了，而是走一段、检查一段、再继续规划。
**我觉得不足的地方**
有反馈也不代表每次都能成功，而且多次调用模型会增加时间和费用。时间长了返回时间更长不够稳定命中缓存也会下降。
**我想引用什么**
我会引用“模型提出方案，外部程序检查，再把具体问题反馈给模型”这个做法。我想借鉴的是反馈和检查，不打算让网约车每走一步都调用 LLM。

## 3. [GridRoute：A Benchmark for LLM-Based Route Planning with Cardinal Movement in Grid Environments](https://arxiv.org/abs/2505.24306)
**这篇讲了什么**
这篇给 LLM 出网格寻路题：告诉它起点、终点和障碍物，让它输出一条只能上下左右移动的路径，再和参考最短路径比较。它也研究把算法步骤写进提示词，看看能不能帮助模型规划。重点是统一任务和评测方式。
**我觉得不足的地方**
网格寻路比真实道路调度简单，没有持续出现的乘客订单，也没有多辆车之间的分配关系。即使模型在这里走出了最短路径，也不能直接说明它会调度网约车。另外，模型可能没有按格式给出路径，这种失败也要算，不能只看成功输出的几条。
**我想引用什么**
我会参考它的算法提示词，以及把“有没有输出、路径是否合法、有效路径是否最短”分开评测的方式。不是很可以作为我的思路参考

## 4. [LM-Nav：Robotic Navigation with Large Pre-Trained Models of Language, Vision, and Action](https://proceedings.mlr.press/v205/shah23b.html)
**这篇讲了什么**
它把语言、视觉和导航模型配合起来用。人给一句路线要求，语言模型先提取里面的地标，视觉语言模型把地标和环境中的图像对应起来，导航模型再负责走过去。我的理解是，它让机器人能利用人描述路线时提到的地标。
**我觉得不足的地方**
它依赖环境中的地标和已有的导航表示，地标认错或者语言理解错，后面就可能走错。它研究的是机器人导航，没有解决我需要的多车订单分配。
**我想引用什么**
这个可以作为路径规划的一部分。我想引用它把自然语言地点和实际地图位置对应起来的思路，比如把“体育馆东门接人”转换成具体上车点，后面的路线仍交给规划模块计算。尤其是和第五篇论文结合起来，去发现一种agent友好的地图就极大的提高定位的准确性！

## 5. [VLMaps：Visual Language Maps for Robot Navigation](https://vlmaps.github.io/)
**这篇讲了什么**
这篇把视觉语言特征和空间地图结合，让机器人能根据语言查询地点和空间关系。地图除了坐标，还能回答“椅子旁边”“桌子和电视之间”在哪里。它也讨论不同类型的机器人共享地图表示。
**我觉得不足的地方**
它主要处理机器人建图和导航。我做网约车时，大致路网是已知的，更需要处理不断变化的订单、车辆和交通状态。地图能被多个机器人使用，也不等于已经解决了多个智能体之间怎么分配任务。
**我想引用什么**
我认可把地图变成 Agent 能理解和查询的形式这个方向，可以参考它组织地点和空间关系的方式。视觉建图这整套东西未必需要照搬，我更关心已知道路地图怎么和动态信息放在一起。这个和第四部分结合就是很不错的机器人导航

## 6. [DualG-MARL：A multi-agent reinforcement learning scheduling algorithm integrating state graph and task graph structural modeling for ride-sharing dispatching](https://www.nature.com/articles/s41598-026-35004-8)
**这篇讲了什么**
它分别把车辆状态和乘客任务建成图，再考虑车与车、订单与订单、车与订单之间的关系，用多智能体强化学习做派单。匹配时会先过滤不合适的候选，再保留一部分有价值的候选，减少重复计算。
**我觉得不足的地方**
我觉得挺好的，就是一些老生常谈的问题，可以持续优化。
**我想引用什么**
这篇和我的想法比较接近。我会参考车辆状态图、任务图和可行候选筛选，作为多智能体调度的参考。之前提到 CNN 也可以考虑，但这篇实际更值得我借鉴的是图结构和车辆、任务之间的关系，不代表我现在就要训练它的整套模型。

## 7. [Optimizing Large-Scale Fleet Management on a Road Network using Multi-Agent Deep Reinforcement Learning with Graph Neural Network](https://arxiv.org/abs/2011.06175)
**这篇讲了什么**
它把道路网络表示成图，用图神经网络和多智能体强化学习安排车队，考虑空闲车辆往哪里移动。车辆决策会参考从订单数据中学到的需求规律，也避免所有车只盯着同一个看起来最好的位置。
**我觉得不足的地方**
这篇我的认可度相对低。对我的选题来说，它更像是帮助判断哪里可能有单、空车应该往哪走的一部分，还不能覆盖我关心的服务目标表达和已有订单承诺。碰到历史数据里很少出现的需求变化时，能不能处理好，我也还不确定。不过不能因为用了历史数据，就直接说它没有用。
**我想引用什么**
暂时不把它当主要参考。

## 8. [LLM+P：Empowering Large Language Models with Optimal Planning Proficiency](https://arxiv.org/abs/2304.11477)
**这篇讲了什么**
它让 LLM 把自然语言任务转换成 PDDL，也就是规划器能读取的问题描述，然后由传统规划器求解，再把计划解释给人。LLM 主要负责把要求表达清楚，真正寻找可行计划的工作交给规划器。
**我觉得不足的地方**
这个就不是属于无人车调度，但是和第四第五部分的agent友好可以相挂钩
**我想引用什么**
这和我工作中尝试做 Agent 友好版 PRD 的思路很像，我认可这一层。我会参考它把自然语言整理成明确对象、状态和目标的做法，用在提示词和目标表达上。这个分工本身已有研究，我需要说清自己具体改了什么。

## 9. [OVDM：Multi-Agent Reinforcement Learning for Order-dispatching via Order-Vehicle Distribution Matching](https://arxiv.org/abs/1910.02591)
**这篇讲了什么**
它把车辆看成智能体，让车辆从候选订单里选择，同时考虑接完这单以后车辆会分布在哪里，尽量让车辆供给和订单需求匹配。训练时考虑联合策略，执行时车辆可以分别决策，不需要车辆之间显式通信。
**我觉得不足的地方**
这个属于前置的了，属于是锦上添花但不是必需品，是基于历史数据使得的车辆分布，一个是车辆分布会出现偶然性偏差，可能会导致部分乘客偶然的接驾时间过长，再有就是我觉得调度的效率优化比车辆分布更有效一点，这样接驾也差不了太多时间。如果这个东西可以自己迭代的话可以考虑，我其实也比较感兴趣
**我想引用什么**
这篇我也认可，比较贴近派单本身。我会参考“当前这单派给谁，会影响下一轮车辆分布”这个考虑，以及车辆智能体的状态和动作设计。它比单纯预测哪里可能有单，更接近我的调度问题。到目的地后对下一轮次派单的影响也是可优化部分

## 10. [On-demand high-capacity ride-sharing via dynamic trip-vehicle assignment](https://people.csail.mit.edu/jalonsom/docs/17-alonsomora-ridesharing-pnas.pdf)
**这篇讲了什么**
它先找出满足容量、等待和绕行限制的候选行程，再通过数学优化决定哪些行程交给哪些车。新订单到来以后，可以继续更新分配和路线。它直接处理多辆车、多个订单和约束之间的关系。
**我觉得不足的地方**
它需要事先明确目标、约束以及行驶时间等输入。如果现实路况和预计时间有差别，原来的安排也可能需要更新。但是它处理的是拼车。
**我想引用什么**
这篇可以作为底层调度器或数学优化部分的参考。自己写一套算法确实是不太可能了，虽然这是拼车的算法，我也可以考虑一下是否可以沿用或再找找不是拼车的算法。
