# NYC TLC 2024-01 请求轨迹审计

日期：2026-10-19。审计对象：NYC TLC 2024 High Volume FHV 行程记录。处理器：DuckDB 1.5.6。原始 Parquet 只读；清洗结果单独保存。详细字段、逐时计数、OD 热点及哈希见 [审计 JSON](../outputs/dispatch_layer/nyc_tlc_hvfhv_2024/audit_2024-01/audit_2024-01.json)。

## 审计发现

`fhvhv_tripdata_2024-01.parquet` 按实际上车时间覆盖 2024-01-01 至 2024-01-31，共 19,663,930 行；但请求时间从 2023-12-31 23:01:55 到 2024-02-01 00:07:07。因此不能只取 1 月文件来构造“1 月请求流”。在已下载的全部 2024 月文件中按 `request_datetime` 过滤 1 月，得到 19,664,474 行，来源是 1 月和 2 月文件；其中 1,405 行的实际上车发生在 2 月。这个 cohort 只覆盖已下载的 2024 pickup 年度文件；可能在 2025 才上车的预订不在本次范围内。

| 检查项 | 结果 |
|---|---:|
| 1 月请求记录（跨 2024 月文件） | 19,664,474 |
| 共享拼车匹配 `shared_match_flag=Y` | 227,967 |
| 请求时间晚于实际上车时间 | 188,248 |
| 实际上/下车顺序无效 | 2 |
| `trip_time <= 0` | 2 |
| 关键时间/区域/行程字段缺失 | 0 |
| 起终区域无法匹配官方 lookup | 0 |
| 1 月上车文件全行 64 位 hash 重复指纹 | 0 |
| 实际行程时间与 `trip_time` 相差超过 60 秒 | 0 |

1 月请求时间 cohort 中有 19,436,507 行标记为 `shared_match_flag=N`。按一车一单研究需要，回放候选进一步只保留：请求时间位于 1 月、拼车匹配标记为 N、请求不晚于上车、上车早于下车、`trip_time>0`、`trip_miles>=0`，且起终区域均能匹配 lookup 的记录。得到 **19,248,258 条**候选请求事件。筛选条件使用了实际事后行程字段，因此这是已完成派遣记录上的整理轨迹，不是无偏的全部潜在请求总体。

候选记录的请求至实际上车间隔中位数为 220 秒，P95 为 541 秒，最大值为 73,837 秒。它只表示历史请求到实际上车的时间差；普通车辆的司机到达时刻未提供。它也不是当前算法的反事实等待结果。现有模拟的 300 秒接驾上限应作为算法实验约束独立执行，不能用历史上车时间替代。

## 回放输入

生成的 Parquet 含 19,248,258 行、184,950,739 字节，字段为来源记录 ID、源文件与源行号、`request_datetime`、相对 2024-01-01 的 `arrival_time_sec`、`pickup_zone_id` 和 `dropoff_zone_id`。没有把实际上车/下车时间、实际行程时长或距离送入调度器输入。源文件和行号可回溯至原始 Parquet；源文件 SHA-256 见原始数据目录的 manifest。

- 回放候选：[request_trace_2024-01.parquet](../outputs/dispatch_layer/nyc_tlc_hvfhv_2024/audit_2024-01/request_trace_2024-01.parquet)
- 机器可读审计：[audit_2024-01.json](../outputs/dispatch_layer/nyc_tlc_hvfhv_2024/audit_2024-01/audit_2024-01.json)
- 可复现脚本：[audit_nyc_tlc_hvfhv_month.py](../scripts/audit_nyc_tlc_hvfhv_month.py)

复跑命令（先安装 DuckDB 1.5.6）：

```bash
python -m pip install duckdb==1.5.6
python scripts/audit_nyc_tlc_hvfhv_month.py --year 2024 --month 1
```

## 适用边界与后续

这份轨迹适合作为区域级历史派遣请求输入，但**尚不能直接运行现有调度模拟器**：当前模拟器的起终点是道路图节点，而 NYC 数据提供 taxi-zone 区域 ID；车队初始位置与逐时可用状态也不在数据中。需要先选定真实道路图及区域到道路节点的映射，再明示合成车队的数量、初始位置与忙闲状态。此外，19.25M 月度候选事件远超现有每小时 100 单、10 车的合成设置，需先确定一致的区域/时段抽样或规模化方案。

审计完成后另做了一次 D0/D1 zone-cost 探索性试跑。试跑仅产生 5 个可行候选、没有多车竞争，且将载客 OD 时间代理为空车接驾时间；因此不是有效的调度性能实验。结论和限制见[探索性试跑记录](dispatch-layer-nyc-tlc-zone-proxy-pilot-2026-10-19.md)。路线层未重跑：该数据仍缺少道路边、边成本和路径轨迹；本审计产物仍只是请求时间与区域的需求输入。
