# R4 100×100 分步调用与预算预检（2026-10-21）

## 结论

**当前 v3 smoke 的每任务 32 次请求上限不能用于正式 100×100 批次。** 十个种子的冻结任务中，离线有向 BFS 得到 130 个传统基线可完成任务的最少边数；其中 **128 个（98.5%）至少需要 33 步**，最多需要 264 步。严格按每次 API 响应提交一步时，32 次上限会让这些任务即使模型一步不犯错也无法完成。此审计没有调用 API，传统基线路线和评估真值未提供给 R4。

R4、R4-A、R4-B 的交互规则和正式调用预算须先冻结，正式批次暂不启动。

## 输入一致性

- 10 张地图与 10 份订单任务文件和纯 LLM v8 逐文件 SHA-256 完全一致（20/20）。
- 10 份正式场景文件原始哈希不同，因为纯 LLM v8 的每个场景额外嵌入了 `road_map`；去掉该冗余快照后，场景、任务、封闭边和真值字段均逐对象一致（10/10）。R4 输入构造应以单独冻结的地图文件为准，不能把该重复 `road_map` 再塞入模型提示。
- 每种子 10 个订单 + 5 个正式任务，共 150 个任务/方法。订单为 70 个精确节点、30 个语义地点任务。三组合计 450 个方法—任务结果。传统结果中 130 个任务有可行路线；10 个非法端点和 10 个不可达场景不在路径步数预算样本中。

## 有向步数统计

离线 BFS 使用冻结地图的有向边，按“起点→上车点 + 上车点→下车点”分别计算最少边数；评估器保存的语义真值只用于离线预算统计，不进入模型输入。

- 可达基线任务：130 个；最少边数总和：17,219。
- 均值：132.45；中位数：123.5；P90：198；P95：226；最大值：264。
- 超过 32 步：128/130；订单任务 99/100，正式场景中可行的基线任务 29/30。

这是基于最少有向边数的**路线长度下界**，不是把传统算法轨迹交给 R4。模型的绕行与被拒动作还会增加请求数。

## 输入规模与费用预检

用正式 100×100 的冻结地图、任务端点（语义真值只用于离线构包）和现有 `build_route_input_package` / `build_r4_stepwise_messages` 代码，对 130 个可达任务逐个构造了 R4 请求。没有调用 API。初始完整提示（系统说明 + 紧凑局部网格 + 任务状态）字节数：中位数 19,898，P90 34,431，最大 42,787；8×8 v3 的完整提示约 2,440 字节。**分步实现每次都重发整张紧凑局部网格**，因此请求数乘以路径步数后，输入规模成为主要成本。

| 每个可达任务的请求方式 | 每组序列化消息字节估算 | 每组输入 token 代理 | 每组输入费用代理 | 三组输入费用代理 |
|---|---:|---:|---:|---:|
| 一步一请求，零违规提议，按最少有向边数 | 420.9 MB | 约 2.188 亿 | ¥656.40 | ¥1,969.19 |
| 一步一请求，按 v3 的 31 次请求/25 条接纳边比例 | 521.9 MB | 约 2.713 亿 | ¥813.93 | ¥2,441.79 |
| 每任务一次完整路线请求 | 每组 2.764 MB | 约 143.6 万 | ¥4.31 | ¥12.93 |

输入 token 代理采用 v3 单次 8×8 smoke 的 `40,270 input tokens / 77,463 serialized message bytes` 比率，并按配置的 `¥0.000003/token` 估算；工具 schema 字节没有计入消息字节分母，DeepSeek 在 100×100 编码上的实际 tokenization 未实测。表内只计输入费。若按 v3 的平均输出 124 token/请求外推，三组另需约 ¥19.22（理想步数）至 ¥23.83（v3 拒绝比例）的输出费，输入加输出约 ¥1,988–¥2,466；完整路线输出 token、重规划反馈、Qwen 本地计算费未计。表中是量级对比，不是账单或上限。之前按 8×8 平均每次调用费用线性外推的三组 ¥273.46 估算**已被本段取代**，原因是漏算每次请求重复发送的 100×100 图输入。

R4、R4-A、R4-B 的消融规则并非都明确要求逐边独立 API 调用，因此“一步一请求”的三组总价仅是同方式假设，不应当作为正式预算。最符合当前研究目标的候选方案是：**每次请求返回完整的有序边序列，每一边附结构化自检；独立程序从第一步开始逐边检查有向边、连续性、边界、上车顺序和禁止重复节点；任何一步不合法则整条提议不接纳，只按已冻结上限发送带校验错误的反馈。**这样保留逐步生成/自检与程序硬校验，但不为每条边单独付一次输入费用。该候选方案尚未修改为正式协议，也尚未做 100×100 输出长度门禁。

## 正式批次前要冻结的规则

1. 选择保持“一次请求输出一步”，还是改成分段提议、程序逐边核验的交互；任何违规边均不得进入权威路线状态。
2. 对 R4、R4-A、R4-B 统一每步 schema、端点门禁、失败状态和请求预算；当前方案的完整路线请求/三次重规划描述与 v3 一步一请求实现尚未完全对齐。
3. 冻结“一次完整路线请求 + 逐边自检”或“一步一请求”的实验口径；当前成本证据支持先评估前者，但不得在未验证前声称已经定案。
4. 对冻结后的方案完成 100×100 输出长度、schema 大小和运行时费用熔断的离线门禁，再单独进行一个获准的正式尺寸单任务验证；不自动启动十种子批次。
