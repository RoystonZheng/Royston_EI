# NYC TLC 多车竞争派生场景

日期：2026-10-19  
用途：为一对一动态派单模拟提供可复现的多订单、多车候选输入。  
状态：派生数据已生成并完成结构核对；尚未运行 D0/D1 调度实验。

## 数据来源与生成

场景由 [`request_trace_2024-01.parquet`](../outputs/dispatch_layer/nyc_tlc_hvfhv_2024/audit_2024-01/request_trace_2024-01.parquet) 中的候选请求派生。该轨迹经过 `shared_match_flag=N`、时序和区域有效性筛选，但仍只代表已派遣/完成行程，存在事后选择偏差。每条订单保留原始 `source_record_id` 作为 `order_id`，起终点使用 `zone_<ID>`，到达时刻相对各场景窗口起点计算。

生成脚本为 [`build_nyc_tlc_multi_vehicle_scenarios.py`](../scripts/build_nyc_tlc_multi_vehicle_scenarios.py)，默认输出到 [`multi_vehicle_competition_scenarios_v1`](../outputs/dispatch_layer/nyc_tlc_hvfhv_2024/multi_vehicle_competition_scenarios_v1/)。脚本只读候选轨迹和数据清单，若目标目录已存在则拒绝覆盖；根清单记录输入轨迹哈希，各场景清单记录订单 JSON、Parquet 的哈希和字节数。

## 输入结构

每个场景目录包含：

- `orders.json`：可实例化为调度实验 `Order` 数据类的订单字段，以及场景 ID、订单数和原始窗口。
- `orders.parquet`：场景 ID、订单/源记录 ID、来源文件与行号、请求时间、相对到达秒数、起终 zone ID。
- `scenario.json`：来源、起终区分布、车队变体、统一的 300 秒接驾上限、0% no-show 假设、输入哈希和限制说明。

示例命令（需要项目使用的 DuckDB 环境）：

```bash
python3 scripts/build_nyc_tlc_multi_vehicle_scenarios.py
```

## 车辆假设与证据边界

车辆 ID 和初始位置均为人工构造，并有意放在各场景订单的上车 zone。这样可以在区域级确定地生成多车候选，不需要把先前试跑中未经验证的完整载客 OD 时间伪装成空车接驾时间；代价是同区上车区级接驾时间为零，也没有区内移动或跨区道路时间。该构造仅适用于验证候选冲突、匹配规则、负载阶梯和输入管线。

NYC TLC 来源记录不包含全量未服务请求、历史可用车队、车辆逐时位置或可验证的道路 ETA。当前数据包不是完整的真实派单回放，不能用来声称 NYC 服务率、等待时间或任何算法性能。数据包构建阶段没有执行 D0/D1，也没有重跑路线层；之后的 C2、C3、C4 运行只检查机制执行，不是正式性能比较。

## 现有调度器接入状态

`orders.json` 中订单及车辆字段可实例化为 `dispatch_experiment.models.Order` 和 `Vehicle`。`DispatchSimulation` 支持注入外部 `RoadMap`、订单、车队和路线 oracle。NYC 专用 oracle 将接驾与载客路线查询分开；C3 只允许同区零成本接驾，跨区接驾标为不可达。通用 `run_dispatch_experiment.py` CLI 仍默认生成随机网格场景。

正式比较仍需可验证的道路时间模型和车辆状态生成/校准方案。训练期 zone OD 中位行程时间仅作为载客段区域代理成本；相同上车区初始化带来的零接驾成本是人工设定。C2–C4 机制检查验证输入、候选和一对一规则，不形成 NYC 服务性能结论。

两方法使用相同场景指纹 `3aae4d3fd25e2b0310ee608dd3a527ce9d41e57d634e166cf2a4103efc10a42d`，首轮选中的订单集合相同，车辆与订单均没有重复；由于三辆车初始位置和成本相同，具体车辆—订单配对的平局打破顺序不同。这个结果支持 C2 输入接入和一对一分配机制可运行；不表示两种算法性能相同或某种方法更优。完整逐轮记录、运行配置和输入哈希保存在各方法 JSON 与 `preflight_manifest.json`。

## 前一阶段拟定的下一步

C2、C3、C4 都已完成机制预检；它们不能替代正式性能实验。2026-10-20 的 DOT 数据审计找到与 C3/C4 日期重叠的 E-ZPass 历史路段时间，但单个快照只有 351 条监测路段、253 条有效时间，15 米吸附后形成 40 个无向分量，不能给当前 C4 的 126 个目的地区域提供完整接驾 ETA；细节见[路段成本数据审计](dispatch-layer-nyc-dot-road-cost-data-audit-2026-10-20.md)。下一步先评估 CSCL 有向拓扑与这些观测边的匹配覆盖，再决定是否构造受限区域子集或扩展多时段实验。在真实车辆位置/空闲状态仍不可得的情况下，车队状态仍需作为明确的模拟假设。

TLC zone OD 代理与 DOT 传感器子网均不支持直接重跑现有路线层；未来如建立 NYC 有向道路图，应作为独立道路图基准，与 100×100 合成路线层结果分开报告。

## 当前结论与下一步（2026-10-20）

前述“匹配 CSCL 并评估是否可用于受限派单”的计划已完成。E-ZPass 到 CSCL 几何/名称匹配有 129/133 条有效曼哈顿读数通过；沿线速度候选仅覆盖曼哈顿 4.233% 的有向道路几何，完整观测图有 67 个弱连通分量。对 C4 790 条历史行程派生单做免费区域接驳的乐观上界筛查，也只有 54 条存在已观测有向路径；这些数据不足以替换完整 C4 成本矩阵或重跑路线层。

后续主实验仍应围绕可完整控制车辆—订单候选成本的 C2/C3 受控竞争场景推进，不能把当前 C4 TLC zone OD 机制检查或 DOT 局部覆盖预检写成真实 NYC 派单性能结果。若继续探索 DOT 数据，先另建并标明范围的受限走廊场景，固定缺失区域处理、区域锚点、车辆初始位置和观测速度合并规则，再决定是否运行。细节见 [`NYC DOT 成本子段映射与 C4 可达性预检`](dispatch-layer-nyc-dot-cost-overlay-preflight-2026-10-20.md)。
