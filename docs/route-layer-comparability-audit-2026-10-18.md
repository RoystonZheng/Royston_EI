# 路线层传统算法与纯 LLM 实验可比性核查

日期：2026-10-18  
范围：`traditional_experiment_v1` 与 `pure_llm_experiment_v7`，100×100 地图、种子 0–9。  
方法：逐种子比对地图/订单文件 SHA-256、正式场景任务数据、价格配置和可视化记录；不重跑路线算法或 API。

## 核查结论

两组使用相同的 10 张地图、相同的订单和正式场景输入。每个种子有 10 个订单（7 个精确节点任务、3 个语义地点任务）及 5 个正式场景。地图与订单 JSON 在两组间逐字节一致；正式场景在忽略纯 LLM 文件中的 `road_map: null` 元数据后，内容一致。Tesla 参考价格配置在每个种子、两组之间一致。

| 项目 | 核查结果 |
| --- | --- |
| 地图 | 100×100，种子 0–9；每个种子的地图文件跨组 SHA-256 相同 |
| 订单 | 每种子 10 个；跨组文件逐字节相同；总计每组 100 个订单任务 |
| 订单构成 | 每种子 7 个精确节点 + 3 个语义地点任务；总计 70 + 30 |
| 正式场景 | 每种子 5 个，类型为可行、边界、非法端点、绕行、不可达；任务与约束相同 |
| 成本价格配置 | 两组每个种子的 `price_profile` 相同 |
| 运行条数 | 两组都覆盖相同的 150 个任务实例（100 个订单 + 50 个正式场景）；传统组每任务跑 3 种方法，共 450 条结果；纯 LLM 每任务跑 1 种方法，共 150 条结果 |

## 有意保留的方法差异

本核查确认的是场景样本和底层地图事实一致，并非方法配置完全相同。传统组比较全图 Dijkstra、局部 Dijkstra、局部 A*；纯 LLM 组使用 `deepseek-flash` 路线规划。两组的任务输入都从同一地图、任务真值和中立局部路线包生成，但模型所见的序列化范式不同：纯 LLM 使用压缩的 `grid-road-v1` 输入；传统方法使用图结构。语义任务也保留方案规定的处理差异：传统语义解析器只使用图规则，纯 LLM 可读取道路特征语义。这是路线层处理因素，不应误报为地图或订单不一致。

因此，适合比较同一任务上的路线合法率、失败类型、计算/调用成本及路线评估结果；不能把“传统组 450 条方法结果”与“纯 LLM 组 150 条方法结果”当成两组任务数不同。全图 Dijkstra 是全图参考；局部 Dijkstra、局部 A* 与 LLM 的路线规划结果应结合各自输入表示和方法边界解读。

## 失败轨迹与违规标注

纯 LLM 的原始结果有 150 条，路线成功数为 0。78 条返回了方向序列，其中包含非法移动；其余失败为模型报告无法规划/解析，以及 1 条输出截断。为使失败也可检查，现已重建这 78 条方向序列并逐步回放：合法前缀单独绘制，全部违规动作记录步号、起终节点、方向和限制类型。共标记 793 个违规动作：624 个单向方向违规、169 个越界动作。首次违规之后的虚线仅代表模型继续提出的路径，不表示可通行或已经执行。

例如 seed 0 的正式可行场景，模型第 5 步尝试从 `node_67_11` 向东到 `node_68_11`；地图只有反方向的单向边，因此此处标为首个违规。图中前 4 步是合法前缀，后续动作继续按“提议”展示并标注其各自违规位置。

两组的逐任务 JSON/HTML 回放与 seed 仪表盘已刷新；这里只重建可视化，没有重新调用 API 或重跑传统算法。

图例也按算法分别说明颜色含义：传统算法用红色实线表示最终路线；纯 LLM 用青绿色实线表示合法前缀/通过校验的路线、红色虚线和叉号表示违规动作、紫色虚线表示首个违规后的模型提议。

后续根据页面空白截图复查发现，详情页脚本在模型提议路线绘制代码块缺少一个闭合花括号，造成整段 JavaScript 解析失败，地图和右侧轨迹区都没有初始化。已修复模板并在渲染测试中加入 Node.js `--check` 语法检查；随后重新生成全部 600 条详情 HTML。四种代表页（两组、订单/正式场景各类）的脚本语法检查通过，清单指向的 HTML 文件均存在。
