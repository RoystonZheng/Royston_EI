## 当前实现

`route_experiment/llm_adapter.py` 提供 DeepSeek Chat Completions 适配器和独立路线校验器，`scripts/run_pure_llm_experiment.py` 使用与传统算法相同的地图、订单、正式场景生成器和费用评估器，但写入独立的 `outputs/route_layer/pure_llm_experiment_v1` 目录。

模型请求只包含任务原话、中立路线输入包、节点/边/道路特征及固定 JSON 输出协议。`true_pickup_node_id`、`true_dropoff_node_id` 等评估真值不进入提示词。模型输出后，程序重新检查节点和边是否存在、方向是否连续、禁行边、上下车点合法性、端点顺序和语义端点匹配，再进行统一的时间、能耗和费用计算。

密钥通过运行时环境变量读取，不写入代码、JSON、HTML、日志或 Git。结果只记录请求模型、服务端返回模型、token 数、延迟、重试次数、校验状态和费用字段。

## API 可用性诊断（2026-10-16）

使用同一运行时密钥发送最小 JSON 请求：`deepseek-v4-flash` 和 `deepseek-flash` 均返回 HTTP 402。随后调用余额接口成功返回 HTTP 200，但响应为 `is_available=false`，账户余额为 `-0.02 CNY`，充值余额为 `-0.02 CNY`。因此当前主要阻塞是账户余额/可用额度，不是 API key 过期；密钥也没有写入实验产物。

此前十种子结果中的 HTTP 400、读取超时和 SSL/连接中断属于另外的请求层问题。由于当时没有保存服务端响应正文，400 的精确原因不能从现有结果反推；大地图请求的输入规模很大，可能同时触发请求限制或连接超时。余额恢复后应先用最小请求做健康检查，再按原种子和原参数补跑失败请求。

## API 可用性复查（2026-10-17）

当前配置仍指向 DeepSeek 官方地址，模型为 `deepseek-flash`。本轮没有发现正在运行的纯 LLM 实验进程。复查时，Python 默认网络请求会采用本机 `HTTPS_PROXY`/`HTTP_PROXY`（`127.0.0.1:7897`）；经该代理连接 `api.deepseek.com` 时在 TLS 阶段出现 `EOF occurred in violation of protocol`。使用 `NO_PROXY=api.deepseek.com`（同时设置小写 `no_proxy`）让请求绕过该代理后，未带凭据的请求收到预期 HTTP 401，TLS 和 HTTP 链路可用；再使用本机配置中的运行时凭据发出一条极小的 JSON 路径请求，收到 HTTP 200，服务端返回 `deepseek-flash`，耗时约 856 ms，token 用量为 38 输入、5 输出。凭据没有写入本记录。

因此，当前“不可用”的直接原因是批次进程沿用系统代理导致 TLS EOF，而不是本次探测时 API 密钥失效或账户额度不足。HTTP 200 仅证明最小请求可用，不证明大地图批次或路线质量已通过。`pure_llm_experiment_v4` 仍只有 seed 0–6 的 105 条记录，状态为 `api_error`；seed 0、1、6 还记录有 HTTP 400，但适配器只保存状态码、不保存错误正文，无法确认这些 400 的具体原因。大地图请求输入很大，需将上下文/请求限制列为待查风险；不能把它写成已证实的唯一原因。

续跑条件：先轮换此前曾在调试输出中暴露的 API key，并将新 key 写回本机 `configs/route_layer/llm_api.env`；然后只对实验子进程设置 `NO_PROXY=api.deepseek.com no_proxy=api.deepseek.com`，在原 `pure_llm_experiment_v4` 输出目录重跑 seed 7–9，再执行 `--consolidate-only` 重建包含 seed 0–9 的总索引。不要重新运行 seed 0–6，以免重复请求和费用。续跑可开始，但十种子实验只有在所有预期轨迹均落盘、请求层错误得到处置且路径校验结果完整后，才能判断是否完成。

## v7 逐条失败与耗电后处理审计（2026-10-18）

根据用户要求，对 `pure_llm_experiment_v7` 已保存的十个种子共 150 条结果做本地后处理；没有发起 API 请求，也没有重跑路线搜索。结果 JSON 保留原始模型输出和失败码，新增 `failure_detail_zh`、`llm_response_received`、`proposal_energy_audit` 与同任务传统算法对照说明；订单/正式场景索引、单条回放、种子总览和根索引均已重建。完整逐条数据见 `outputs/route_layer/pure_llm_experiment_v7/failure_energy_audit.json`。

分类结果：150/150 条均收到 API 响应，请求层失败为 0。78 条完整方向序列均未通过有向道路校验，合计 793 个违规动作（624 次逆单行方向、169 次越界）。另有 71 条结构化 `status=failed` 响应未返回路线步骤；这正是此前页面出现“失败但违规为 0”的原因：没有候选移动可供计算违规数，不代表 LLM 没有响应。剩余 1 条响应的 JSON 被截断，但可恢复 162 个方向步，其中 87 步违规（6 次逆单行、81 次越界）；此条已标为部分路线回放，不作为完整路径。

71 条无路线步骤的失败按种子分布为：seed 0–9 分别 6、10、6、7、5、8、9、8、4、8 条（订单 / 正式场景分别为 4/2、6/4、3/3、5/2、3/2、5/3、4/5、5/3、2/2、6/2）。43 条订单失败对应的同一任务均由 3 种传统算法成功找到有效路线，因此是 LLM 的地点解析或路线规划失败，不是地图不可达。正式场景 28 条无路线响应中，20 条对应方案预设的非法端点/不可达场景；另 8 条是可行场景中的 LLM 失败，同任务传统方法成功。截断的边界场景响应单独计为部分路线，不计入上述 28 条。

对 78 条完整非法提议，按 `energy_v1` 分别记录完整提议路线估算和违规前合法前缀估算：完整提议累计 154.16025 kWh，合法前缀累计 19.03060 kWh。截断响应可恢复前缀估算 2.94940 kWh，其中合法前缀 0.29360 kWh。此处累计值仅是多条模型提议路径的假设估算总和，不是实验车辆的实测或实际执行耗电；已单独保存，未写入有效路线 `resources.energy_kwh` 或有效路线费用。无路线步骤的 71 条结果记为“不适用/未估算”，不当作 0 kWh。

估算口径：有对应方向边时使用该边属性；模型反向走单行时使用反向边属性作为路段代理；两向均无边或越界时，使用地图中位路段长度、拥堵等级和信号延迟作为代理，并逐条记录精确边、反向推断边和代理边数量。完整/部分路径分别标记，避免将假设值冒充实测耗电。

边界诊断：提示中确实包含边界坐标、压缩方向掩码定义、合法端点字段、禁行边列表和“遵守端点/禁行边”要求；但缺少明确的逐步规则，例如每个方向动作都必须由当前节点的对应有向边授权、不能跨出坐标边界。更关键的是，纯 LLM 一次性生成长路线，校验器只在响应后拒绝非法动作，没有生成时的硬约束或基于校验错误的重规划。因此这次失败说明生成端约束不足；后续若改提示或加入逐步工具校验，应作为单独版本/实验条件，不能回写成 v7 原方法。

证据类型：已完成实验产物的派生审计 + 同任务传统基线对照 + 150 个 HTML 脚本语法核验；没有新增模型调用。审计工具为 `scripts/audit_pure_llm_failures.py`，逐项页面从 `outputs/route_layer/pure_llm_experiment_v7/index.html` 进入。
