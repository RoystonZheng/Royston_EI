# R4 输入格式离线预检（2026-10-19）

## 结论

Qwen 和 DeepSeek 不需要使用逐字相同的 JSON 或提示词。它们负责不同阶段：Qwen 根据自然语言和道路特征定位节点；DeepSeek 根据已确定的节点和有向路网搜索路线。两边必须共享一致的地图事实、节点 ID、道路方向、成本口径和地图版本，但可以按职责生成不同输入视图。

本次评估了把 DeepSeek 地图改成“逐节点显式出边”的候选格式。它让每条边的目标、方向和成本更直观，也能与 strict 输出 schema 的允许边逐条对应；但在 100×100 seed 0 的代表性任务中，地图序列化从约 12 KB 增至约 314 KB，约为原来的 25.8 倍。因此没有把候选格式设为 R4 默认输入，也没有为了验证它而调用 API。

R4 继续使用 `directional-cost-grid-v1`：每个节点固定按 E/W/N/S 编码出边，`.` 表示该方向无出边，其余字符通过成本表查到单边时间和距离。该格式同样精确表达有向图，并与 strict 输出约束中的真实允许边集合离线核对。

## 离线检查

- 从 v13 存档重建同一 8×8 任务：64 个节点、205 条有向边。原紧凑格式的用户消息为 2,933 字节；显式索引邻接候选为 8,788 字节。连同 system 提示和相同 strict schema，序列化总字节从 7,435 增至 13,005，约增加 74.9%。
- 对传统组 seed 0 的 100×100 地图首个语义任务做尺寸预估：局部包为 2,726 个节点、9,864 条有向边。尺寸审计把存档真值节点 ID 当作“已解析端点”来估算包大小；离线候选 JSON 中它们作为普通路线查询端点出现，但没有发送给模型，也没有作为模型结果。显式邻接候选的地图部分为 313,636 字节；紧凑地图部分为 12,177 字节。
- 候选格式 8×8 的每一条边都与地图包及 strict schema 对应，没有暴露评估真值。
- 当前代码重新生成的 v13 system/user 消息与存档哈希一致，确认活跃输入格式没有改变。
- 本次 API 请求数为 0，Qwen 本地推理次数为 0。字节数不是 tokenizer 输出，不能直接换算为 API token 或费用。

## 对实验的影响

这组预检只用于输入格式决策，不能证明显式邻接一定提高路线成功率，也不能解释 DeepSeek 在 v12/v13 中为何返回 `unable_to_construct_route`。v12/v13 收到相同的紧凑输入并返回相同结果，只能确认该任务上重复失败；不能归因为 Qwen/DeepSeek 格式不一致。

后续 R4 烟雾应继续沿用紧凑有向网格及现有 strict 边约束。若还要尝试显式邻接，需要先单独评估 API 输入上限和费用，再决定是否值得做一次受控小图验证；它不应直接进入 100×100 批次。
