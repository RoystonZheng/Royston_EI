# 调度层多 Agent、Codex、数学优化器与神经网络实验设计

日期：2026-10-23  
状态：按用户 2026-10-23 决定，将神经网络并入首轮组合方法；D8 已实现并开展 pilot，正式多窗口批次仍待完成。  
研究范围：单乘客订单的一对一无人网约车动态调度，不含拼车、路线算法比较或真实道路部署。

## 1. 研究问题

在相同已到达订单、车队状态、车辆—订单候选和硬约束下，分层的多车辆 Agent、LLM 策略建议、神经网络候选评分及集中式数学优化器，能否在可验证的前提下改善订单服务与等待表现，同时保持合理的空驶、能耗、计算和模型调用成本？每个模块须通过消融分别评估，不以“组合更复杂”推断效果更好。

## 2. 总体架构

```text
已到达订单 + 当前车辆状态
          │
          ▼
统一候选生成与路线成本代理
          │
          ▼
每车 Vehicle Agent：提出本车可行订单候选
          │
          ├── MLP 候选排序（D8，与 Codex 在同一主方法中）
          │
          ├── Codex 低频策略建议（每次模拟最多 1 次）
          │
          ├── 最大匹配容量保护（Codex 与 MLP 筛选后）
          │
          ▼
集中式数学优化器：全局一车一单匹配及既有承诺处理
          │
          ▼
统一输出校验器 → 仿真执行 → 记录等待、服务、空驶、能耗、时间和调用用量
```

车辆 Agent 只能筛选/排序当前可见候选；Codex 只能给受限的 `linear_clip` 参数，不能直接派单、改路线或放宽最大等待、既有承诺、一车一单等硬约束；神经网络只提供候选排序分数。最终匹配、可行性检查和失败回退均由确定性程序控制。

## 3. 方法组

| 方法 | 定义 | 识别的模块作用 |
|---|---|---|
| D0 | 最早截止时间优先的最近可行车贪心 | 简单规则基线 |
| D1 | 完整可行候选上的集中式数学优化器 | 全局匹配作用 |
| D2 | Vehicle Agent + 固定人工情境函数 + 优化器 | Agent/候选筛选作用 |
| D3 | Agent + 离线情境函数代理 + 优化器 | 不产生模型调用的策略层消融 |
| D6 | Agent + Codex CLI 一次性生成情境参数 + 优化器 | 不含学习排序的组合消融 |
| D7 | D6 + 最大匹配容量保护 | 容量保护组件消融 |
| D8 | Agent + Codex + 成对排序 MLP + 最大匹配容量保护 + 优化器 | 本轮主方法；NN 在第一轮实验中直接集成 |
| D5 | 纯 LLM 直接输出匹配 | 已完成的纯 LLM 参照组，保留原结果和后端口径 |

正式比较保留 D2、D6、D7、D8 配对组；D6/D7 是组件消融，不再定义成先完成的独立阶段。D8 是组合方法的主要实验对象。

- 数据包：`outputs/dispatch_layer/nyc_tlc_hvfhv_2024/three_method_benchmark_v1`，固定 C2、C3、C4-F1/F2/F4 案例、车辆配置、区域 OD 成本代理、订单序列和 SHA-256。
- 机制 pilot：C3 多区 44 单/18 车、seed 0 的 D6 已完成；另在 C4 790 单/F1 12 车/seed 0 完成 D6/D7 配对 pilot。D0/D1/D2/D5 的既有结果仅在输入哈希与代码/约束版本核对通过后复用。
- 正式扩展：使用多个相互独立的 TLC 时间窗口与 C4 车队配置 F1/F2/F4；在同一输入窗口内配对 D2、D6、D7。不要把同一固定订单窗口仅更换仿真 seed 后重复运行当成独立需求样本。
- 所有方法使用同一完整、方法中立候选表、时间线、路线成本代理、最大接驾等待、车辆承诺、优化目标和独立输出校验器。Agent 内部过滤不能改写共享输入。
- 每次决策只看已到达订单，不得读取未来订单。固定案例上的 seed 重复主要反映仿真/LLM 决策变动，不等于独立 NYC 需求样本。

数据限制：TLC 历史记录对应已派遣/完成行程，没有拒单、未服务请求和真实车队状态；车辆位置及空驶接驾成本为合成/区域级代理。因此报告只能解释为受控机制仿真，不能称为真实 NYC ETA、服务率或运营改善。

## 5. 首轮 D6 实施口径

1. 当首个已到达订单触发调度时，将当前订单数、当前车况汇总、硬约束可行候选数和候选等待/ETA 摘要发给 `codex exec --json`。
2. 固定 `gpt-5.6-luna`、low reasoning、零重试、每次模拟最多 1 次。使用 JSON Schema、空临时工作目录、只读沙箱、禁用工具和 API key 环境变量；保留原始 JSONL、prompt、最终 JSON 及 SHA-256。
3. Codex 只返回 `linear_clip` 的 `base` 和 7 个权重。程序验证 `base ∈ [120,300]` 秒、每个权重 `∈ [-30,30]` 且数量为 7；不合法、超时、工具事件或无 usage 时留痕并使用固定规则回退，不重发请求。
4. 当前 Agent 用该函数从硬约束可行边中筛选候选；若某车筛选后无候选，恢复该车全部硬约束可行边。集中式优化器完成最终匹配；本地 validator 再检查所有硬规则。
5. 每次模拟只进行一次策略生成，不把运行期间的未来状态输入首次 prompt；本实验不让 LLM 输出分配结果。

首轮 D6 属于集成 pilot，不以一个 seed 宣称性能提升。必须同时报告模型参数是否被接受、工具调用/错误、校验错误、回退次数、完成订单、等待、空驶、能耗、决策时间和 token。

**Agent—LLM 放置说明：**当前代码为每辆车创建一个本地 `VehicleAgent`，这些 Agent 使用同一组由 Codex 生成的 `linear_clip` 参数；每次模拟只在共享调度层发起一次 Codex 调用，没有逐车独立的 LLM 调用。它符合 2026-10-16 流程图中“LLM 可插拔、优化器最终分配”的方案，也让模型输出进入所有车辆 Agent 的候选筛选；但若将研究记忆库“每车 Agent 的工作流中包含 LLM 环节”解释为每个 Agent 都必须执行独立模型步骤，则当前 D6/D7 是共享策略变体，尚未完全满足。正式 P2 批次前应冻结此口径，论文不可写成“每车分别调用 LLM”。

## 6. D7 最大匹配容量保护：机制与创新边界

每轮在统一硬约束可行候选图 `G_t` 上先运行 Agent/情境函数筛选，得到 `G'_t`。用二分图最大匹配计算完整图和筛选图的容量 `K(G_t)` 与 `K(G'_t)`。若筛选导致 `K(G'_t) < K(G_t)`，程序按冻结顺序逐条恢复被筛除的硬可行边，直到 `K(G'_t) = K(G_t)`：

1. `max(0, predicted_wait_sec - context_threshold_sec)` 升序；
2. 预计接驾等待升序；
3. 空驶距离升序；
4. `candidate_id` 字典序。

之后仍由原集中式优化器按既有词典序目标选择最终匹配，统一 validator 再检查承诺、一车一单和最大等待。保护器只恢复已有硬可行边，不增加或改写候选、不放宽硬约束。保证范围限于**当前决策快照的最大匹配基数**，不等于全程服务率或未来系统容量保证。

本文将“情境过滤后的最大匹配容量保护”作为一项小而可检验的设计贡献候选，不宣称首创。既有研究已分别涉及 LLM 联合派单/重定位、派单中的自适应图剪枝，以及局部二分图匹配与 ILP；需要进一步做专门文献查新后，才能写成稳固的新颖性结论：[LLM-ODDR](https://arxiv.org/abs/2505.22695)、[Reinforcement Learning in the Wild](https://arxiv.org/abs/2202.05118)、[BMG-Q](https://arxiv.org/abs/2501.13448)。当前要检验的差异是：在相同候选、相同 Codex 策略参数和相同优化器下，过滤边集前显式比较最大匹配数，只在容量下降时恢复边。

## 8. MLP 候选排序实现口径

- D8 在首轮组合方法中直接启用 MLP；每车 Agent 先做硬约束与 Codex 情境筛选，再按 MLP 分数保留每车 Top-K 候选。最大匹配容量保护随后恢复筛选导致容量下降时必需的可行边；集中式优化器仍作最终分配。
- 标签来源：在训练时间窗的相同快照运行 D1，将 D1 选中的候选边作为正例，只与共享车辆或共享订单的未选可行边构造成对排序样本。标签表示“模仿当前优化器”，不是真实司机选择或订单成败标签。
- 特征：已有当前状态特征，加上归一化接驾等待、接驾距离、载客距离、载客时长及下一单衔接标记。模型只读取当前候选快照，不读取未来订单。
- 模型：PyTorch CPU 小型 MLP（12→16→8→1），成对 softplus 排序损失；训练种子、轮次、标准化参数、D1 文件哈希、特征顺序和模型 SHA-256 均写入审计文件。默认每车 Top-8，作为冻结 pilot 参数。
- Pilot 时间切分：用 C2（2024-01-20 21:54）和 C3（2024-01-17 20:00）D1 记录训练，在 C4-F1（2024-01-20 23:20）留出评估；不同窗口订单 ID 已核对无重叠。多个配置仍只覆盖少数历史窗口，不足以支持泛化结论。
- 指标：训练集成对命中率只作为拟合诊断；同时报告 C4-F1 服务/等待/空驶/能耗代理、候选剪枝量、容量恢复、validator、求解时间和模型加载/评分耗时。D1 标签命中不能解释为真实运营收益。

## 9. 指标与统计

主结果：服务订单数/率（限模拟代理）、平均与 P95 接驾等待、未服务/超时数、既有承诺违规、下一单衔接成功率。  
成本与机制：空驶距离、能耗代理、候选压缩率、回退、求解器和总决策时间、Codex 调用数、输入/缓存/输出/reasoning/总 token。

在输入哈希、方法版本和多个独立需求窗口全部核验后，以时间窗口为统计配对单元，报告配对差值、均值/标准差和区间估计。只有固定窗口而没有独立需求样本时，重复 seed 不得伪装成独立样本。五个固定案例不作为 NYC 总体随机样本，不据此外推真实城市表现。Codex CLI 用量按 JSONL `turn.completed.usage` 记录；官方 token 费率等值与 Codex 账号实际扣款分开，账号账单不能从 JSONL 推算。
